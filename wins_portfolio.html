01 / (주)홈초이스 — 콘텐츠 메타데이터 수집 파이프라인

손으로 입력하던 메타데이터를 매일 자동으로 모으는 파이프라인으로 바꿈

OTT 서비스 오초이스에 올라가는 영화 메타데이터를 담당자가 외부 사이트에서 하나씩 옮겨 적고 있었습니다. 수집부터 정제, 적재까지 한 번에 도는 파이프라인을 만들고 컨테이너로 묶어 매일 실행되게 했습니다.

  • Challenge

    수작업 입력이라 건수가 늘수록 누락과 오타가 쌓이고, 오류 없이 끝나도 실행마다 수집 건수가 달라지는 상태

  • Approach

    Python/Selenium으로 수집과 필드 정제를 구현하고 Docker 컨테이너 + Cron 일 1회 스케줄로 운영. 실행별 수집 건수를 기록해 누락 구간을 좁혀 원인 수정

  • Result

    1,000건 이상을 평균 10분 내 수집, 반복 수작업 제거

02 / 아우토크립트 — 데이터 정제 및 DB 이관

같은 자산이 파일마다 다르게 적힌 엑셀을 하나의 기준 데이터로 만듦

조직도와 IT 자산 현황이 담당자마다 다른 엑셀에 나뉘어 있어 같은 자산이 파일마다 다르게 적혀 있었습니다. 테이블 구조를 먼저 설계하고 데이터를 그 기준에 맞게 정제한 뒤 Spring Boot/React 기반 시스템으로 옮겼습니다.

  • Challenge

    표기가 제각각이고 누가 언제 고쳤는지 남지 않아 어떤 값이 맞는지 판단할 기준이 없는 상태

  • Approach

    MySQL 테이블 설계 후 엑셀 데이터를 기준에 맞춰 정제/이관. 이관 후 원본과 건수를 대조하고 요청/응답 로그로 누락 건 추적

  • Result

    실사용 데이터 2,394건(인원 306명/자산 1,471건) 이관, 사번 자동 채번과 SW 라이선스 만료 자동 경고로 입력 단계부터 품질 관리

콘텐츠 발행, 인코딩, 배포를 담당자가 단계마다 확인하며 넘기고 있었습니다. 단계별 작업을 Quartz 배치 잡으로 나누고 DB 상태값을 보고 다음 잡이 이어받게 만들었습니다.

04 / 개인 프로젝트 — 실패 데이터 재처리 구조

전송이 실패해도 데이터를 잃지 않는 구조를 먼저 만듦

외부 시스템이 SAP OData API로 주문을 보내는 상황을 Mock SAP 서버로 재현했습니다. 파이프라인은 상대 시스템이 응답하지 않는 순간이 반드시 오기 때문에, 실패한 건을 남기고 다시 보내는 구조에 시간을 썼습니다.

  • Challenge

    전송이 실패하면 어떤 데이터가 빠졌는지 알 수 없고 다시 보낼 방법도 없는 단순 호출 구조

  • Approach

    Spring Boot/Spring Data JPA로 전송 서비스를 만들고 실패 건을 PostgreSQL에 저장, 재처리 API와 전송 현황 모니터링 구현. Docker Compose로 서버와 DB를 함께 기동

  • Result

    실패 건을 건별로 확인하고 다시 보낼 수 있는 구조 완성 (github.com/justinnn980/SAP)

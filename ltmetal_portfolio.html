01 / 아우토크립트 — 현업 요구 분석 / 업무 모듈 개발

담당자마다 따로 쓰던 엑셀을 하나의 원본을 보는 시스템으로 바꿈

조직도와 IT 자산 현황이 담당자마다 다른 엑셀 파일에 나뉘어 있어 같은 자산이 파일마다 다르게 적혀 있었습니다. 실제로 쓰는 사람들의 처리 순서를 먼저 정리하고, 그 흐름대로 화면과 서버, DB를 직접 설계했습니다. 자재/설비 대장을 시스템으로 옮기는 일과 같은 구조입니다.

  • Challenge

    파일을 복사해 쓰는 구조라 누가 언제 고쳤는지 남지 않고, 덮어쓰면 현황이 깨지는 상태

  • Approach

    Java/Spring Boot REST API, React 화면, MySQL 테이블을 단독 설계/개발. 입사자 처리를 정보입력 → 기기지급 → 계정생성 → 완료 4단계 화면으로 표준화하고 사번 자동 채번, SW 라이선스 만료 자동 경고 추가

  • Result

    실사용 데이터 2,394건 이관. 배포 후 생긴 CORS 오류와 이관 누락은 요청/응답 로그로 추적해 해결하고 운영 중 기능 계속 개선

02 / 개인 프로젝트 — ERP 인터페이스 연동 구조

ERP로 보내는 것보다, 실패한 건을 잃지 않는 구조를 먼저 만듦

외부 시스템이 SAP OData API로 주문을 전송하는 상황을 Mock SAP 서버로 재현했습니다. ERP 연동은 상대 시스템이 응답하지 않는 순간이 반드시 오기 때문에, 호출 성공보다 빠진 데이터를 찾아 다시 보내는 구조에 시간을 썼습니다.

  • Challenge

    전송이 실패하면 어떤 주문이 빠졌는지 알 수 없고 다시 보낼 방법도 없는 단순 호출 구조

  • Approach

    Spring Boot/Spring Data JPA로 전송 서비스를 만들고 실패 건을 PostgreSQL에 로그로 저장, 재처리 API와 전송 현황 모니터링 구현. Docker Compose로 두 서버와 DB를 함께 기동

  • Result

    실패한 전송을 건별로 확인하고 다시 보낼 수 있는 연동 구조 완성 (github.com/justinnn980/SAP)

03 / (주)홈초이스 — 서버 운영 / 보안 / 장애 대응

재연결로 넘어가던 통신 장애를 구조를 바꿔 끝냄

서버와 외부 시스템 사이 통신이 갑자기 끊기는 일이 반복됐습니다. 다시 연결하면 바로 복구됐지만, 원인을 모른 채 넘기면 같은 장애가 또 생긴다고 봤습니다. 생산 현장의 시스템이라면 그 몇 분이 라인 정지로 이어집니다.

  • Challenge

    복구는 되지만 원인이 확인되지 않아 같은 장애가 되풀이되는 상태

  • Approach

    방화벽 기록을 시간순으로 추적해 중계 서버 IP 변경이 원인임을 확인. 바뀐 주소를 매번 다시 등록하는 대신 EC2 Elastic IP로 주소를 고정하고 SSL을 적용하는 구조로 재구성

  • Result

    IP가 바뀔 일이 없어져 방화벽 정책과 어긋나는 상황 자체가 사라짐

04 / 프로젝트 — 현장 영상 실시간 AI 판단

현장에서 쓸 수 있으려면 정확도보다 오탐부터 줄여야 했음

카메라 영상에서 사람이 쓰러지는 순간을 판단해 알리는 시스템입니다. 알림이 자주 틀리면 현장에서는 결국 알림을 끄게 되기 때문에, 탐지 성능 수치보다 잘못 울리는 알림을 줄이는 데 집중했습니다. 제조 현장의 이상 감지와 품질 판정도 같은 기준이 필요하다고 생각합니다.

  • Challenge

  • Result

    오탐률 30% → 10% 이하, 25FPS 이상 실시간 처리

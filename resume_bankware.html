06
정정 전표 — 장애와 개선
Incident & Improvement

운영 중 실제로 겪은 장애를 원인까지 추적해 재발하지 않도록 구조를 바꾼 기록입니다.

정정
Proxy 서버 IP 변경으로 대형 파트너사 연동이 반복 중단
상황
LG헬로비전 연동 API 운영 중, 외부 SO 서버 방화벽이 자사 Proxy 서버를 차단하는 장애가 반복 발생, 서비스 중단이 세 차례 이어짐.
원인
AWS 로드밸런서 환경에서 EC2 재시작 시 Proxy 서버의 Public IP가 자동 변경된다는 점을 설계 단계에서 고려하지 않음. 파트너사 방화벽은 고정 IP만 허용.
개선
EC2 Proxy 서버에 Elastic IP를 할당해 고정 IP 구조로 재설계, 이후 파트너사 화이트리스트를 한 번만 등록. SSL 미적용 구간을 찾아 전 구간 HTTPS 전환까지 함께 수행.
교훈
외부 시스템과 연동하는 서비스는 설계 단계부터 인프라 환경 특성(IP 변동성, 네트워크 정책)을 먼저 리스트업하는 습관이 생김.
정정
JPA 기본 Lazy Loading을 그대로 썼다가 N+1 쿼리 발생
상황
Study Tracker API에서 학습 목록 조회 시, 데이터를 100건 이상 넣고 나서야 쿼리가 수백 건 발생하는 것을 발견.
원인
"JPA가 알아서 최적화해줄 것"이라 가정하고 실제 발생 쿼리 수를 측정하지 않은 채 조회 로직을 설계함.
개선
JPQL Fetch Join과 복합 인덱스 2개(user_id,id / user_id,completed,id)를 설계해 N+1 해결, @Cacheable + Redis TTL 60초로 반복 조회 부하까지 제거.
교훈
이후 모든 조회 API를 설계할 때 "몇 건일 때 쿼리가 몇 개 발생하는가"를 먼저 측정하는 습관이 생김.

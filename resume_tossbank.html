Why I Build

문제를 정의하는 개발자

기능을 구현하는 방법은 이제 AI도 빠르게 알려줍니다. 저는 그 앞 단계, 진짜 문제를 찾는 역할에 집중합니다.

개발자는 단순히 고객이나 사용자가 원하는 기능을 그대로 만들어주는 사람이 아니라고 생각합니다. 예를 들어 고객이 "매번 작성하는 엑셀 업무를 자동화해 주세요"라고 요청했다고 가정하면, 엑셀 데이터를 자동으로 처리하는 프로그램 자체는 이제 개발자뿐 아니라 AI를 통해서도 쉽게 만들 수 있습니다.

하지만 실제로 사용자와 이야기를 나눠보면 문제의 본질은 엑셀 작업이 번거로운 것이 아니라, 여러 사람이 각자 파일을 관리하면서 데이터가 중복되거나 누락되고 최신 데이터를 확인하기 어렵다는 것일 수 있습니다. 이 경우 처음 요청받은 엑셀 자동화를 그대로 구현하는 것보다, 데이터를 하나의 데이터베이스에서 관리하고 필요할 때만 Excel로 내보낼 수 있는 시스템을 만드는 것이 더 적절한 해결책입니다.

"요청받은 기능을 만드는 개발자"가 아니라 "사용자의 진짜 문제를 찾아 기술로 가장 적절한 해결책을 제시하는 개발자"

AI가 개발 과정의 많은 부분을 대신할 수 있는 시대일수록, 사용자의 말을 이해하고 숨겨진 요구사항을 발견하며 이를 쉬운 언어로 설명하고 더 나은 방향을 제안하는 능력이 더욱 중요해진다고 생각합니다. 토스뱅크처럼 복잡한 금융 로직과 규정이 얽힌 서비스일수록, 요구사항 하나를 그대로 구현하기보다 그 뒤에 있는 운영/리스크/사용자 맥락까지 함께 고려한 설계가 필요하다고 생각합니다.

01 / (주)홈초이스 — 파트너사 앱 전환 및 인프라 안정화

"앱 전환을 도와달라"는 요청 뒤에 있던 진짜 문제, 통신 구조 자체의 불안정성

전국 디지털케이블TV 가입가구에 VOD를 공급하는 국내 유일 사업자에서, 처음 받은 요청은 LG헬로비전(가입자 343만)/딜라이브(매출 3,500억) 두 대형 파트너사의 앱을 자사 서비스로 전환해달라는 것이었습니다. 그대로 화면만 바꿔 붙였다면 중계 서버의 IP가 바뀔 때마다 방화벽 정책에 막혀 통신이 끊기는 문제가 반복될 상황이었습니다.

  • Challenge

    단순 UI 전환 요청 이면에, 중계 서버 IP 변경 시 방화벽 정책으로 앱-서버 통신이 전면 차단되는 구조적 문제와, 두 파트너사가 서로 다른 DRM(NCG/Multi)을 쓰는 문제가 함께 있었습니다

  • Approach

    증상(통신 두절)을 매번 임시 대응하는 대신 중계 서버에 고정 IP(EIP)를 할당해 원인 자체를 제거하고, HTTP → HTTPS 전환 시 SSL 인증서를 적용해 전 구간을 암호화 통신으로 재구성했습니다. 서로 다른 두 DRM 체계는 단일 재생 구조로 통합했습니다

  • Result

    재발 방지 구조로 통신 장애를 근본 해결했고, 콘텐츠 화면은 앱 배포 없이 반영되도록 웹 분리 구조까지 함께 구축해 이후 운영 대응 속도를 높였습니다

02 / 개인 프로젝트 — Study Tracker API

"Todo API를 만들어보자"가 아니라, 실서비스라면 반드시 필요한 문제를 스스로 정의

학습 Todo를 관리하는 REST API를 기획부터 배포까지 혼자 구현했습니다. CRUD 기능을 완성하는 데서 멈추지 않고, 실서비스라면 반드시 마주칠 인증/성능/동시성 문제를 스스로 찾아 정의하고 해결했습니다.

  • Challenge

    Todo 번호만 알면 다른 사용자 데이터에 접근 가능한 인가 취약점, 통계 조회마다 반복되는 DB count 쿼리, 중복 클릭/재전송으로 인한 데이터 중복 생성 위험을 직접 발견했습니다

  • Approach

    jjwt 없이 HMAC-SHA256으로 JWT 서명을 직접 구현해 인증 흐름을 처음부터 이해했고, Redis에 사용자별 통계를 60초 캐싱하며 데이터 변경 시 즉시 무효화하는 전략을 설계했습니다. 요청마다 Idempotency-Key를 부여해 같은 요청이 반복돼도 409로 차단하도록 만들었습니다

  • Result

    단위/통합 테스트 60건, GitHub Actions → Docker → Render로 이어지는 CI/CD 파이프라인, Actuator 상태 확인 API와 운영 Runbook까지 구축해 "만들었다"가 아니라 "왜 그렇게 만들었는지 설명할 수 있는" 상태로 완성했습니다

지금 만들며 성장하고 있는 방식

토스뱅크가 다루는 복잡도 높은 은행 서비스에 기여하기 위해, 지금도 구조 설계 감각을 직접 만들며 넓히고 있습니다.

저는 "공부만 하지 않는다. 각 단계마다 코드, 실행 결과, 설명을 남긴다"는 원칙으로 백엔드 학습 로드맵을 스스로 세워 실행하고 있습니다. 합격 기준을 "알고 있다"가 아니라 "만들었고, 왜 그렇게 만들었는지 말할 수 있다"로 두고, Java 객체지향 설계부터 Spring Boot API 구조, 인증/캐싱/동시성 문제까지 각 단계를 직접 구현하며 검증해왔습니다.

Study Tracker API에서는 인증/캐싱/멱등성 처리를 직접 설계했고, 담아(Dama) 프로젝트에서는 Kotlin 기반으로 도메인을 분리하고 Refresh Token Rotation 구조를 직접 구현했습니다. 두 프로젝트 모두 테스트 코드와 운영 문서를 함께 남기며, 기능 구현에서 끝나지 않고 유지보수 가능한 구조로 완성하는 습관을 실제로 만들어가고 있습니다.

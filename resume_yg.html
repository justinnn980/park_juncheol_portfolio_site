Section 02
콘텐츠 서비스 운영에서 부딪힌 문제들
ISSUE 01
화면 하나 바꾸는데 앱 심사/재배포가 필요한 문제
콘텐츠 화면 변경마다 앱 심사 대기 → 웹으로 화면 분리 → 앱에서 WebView로 연동 → 배포 없이 즉시 반영
영화 포스터가 나열되는 탐색 화면처럼 자주 바뀌는 화면을 앱 내부 화면으로 관리하면 수정할 때마다 앱 심사를 거쳐야 했습니다. 해당 화면을 웹으로 직접 분리 구현하고 WebView로 연동하는 구조로 전환해, 이후 콘텐츠나 배너를 앱 배포 없이 바로 반영할 수 있게 됐습니다.
ISSUE 02
웹 전환 후 첫 화면이 느려진 문제 — 지표로 증명한 개선
체감 로딩 저하 발생 → 구간별 소요 시간 측정 → 스켈레톤 UI + Lazy Loading + CDN 적용 → FCP 39%, LCP 10.8% 개선
앱 내부 화면을 웹으로 전환한 뒤 첫 화면 표시가 느려졌습니다. 감으로 판단하지 않고 로딩 구간별 소요 시간을 측정해 병목을 특정한 뒤, 화면에 보이는 콘텐츠부터 우선 로딩하고 이미지가 늦게 뜨는 구간에는 스켈레톤 화면을 먼저 보여주는 방식으로 개선했습니다.
ISSUE 03
서로 다른 두 서비스의 영상 보호 방식을 하나로 통합
NCG / Multi DRM 이원화 → 플레이어 구조 직접 분석 → 보호 방식 무관 단일 재생 구조로 재설계 → 유지보수 복잡도 절감
두 파트너사가 서로 다른 영상 보호 방식(NCG, Multi DRM)을 사용해 재생 구조를 통일하기 어려웠습니다. 방식마다 별도 구조를 만들면 유지보수 비용이 커진다고 판단해, 기존 플레이어를 직접 수정해 보호 방식과 무관하게 동일한 화면과 시청 흐름을 유지하도록 통합했습니다.
ISSUE 04
서버 IP 변경으로 인한 앱-서버 통신 두절
방화벽 정책으로 통신 차단 → 임시 우회 대신 원인 추적 → 고정 IP + SSL 구조로 재구성 → 통신 장애 재발 차단
중계 서버의 IP가 변경되면서 방화벽 정책에 의해 요청이 차단돼 통신이 두절됐습니다. 임시로 덮지 않고 중계 서버에 고정 IP를 할당해 근본적으로 해결했고, 암호화되지 않았던 구간에는 SSL을 적용해 앱-서버 전 구간을 HTTPS로 전환했습니다.

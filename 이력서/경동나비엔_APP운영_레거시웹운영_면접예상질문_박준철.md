# 경동나비엔 면접 준비 — APP 운영(1순위) / 레거시 웹 운영(2순위)

AI/자동화(AX)로 지원했으나 서류전형에서 APP 운영(1순위), 레거시 웹 운영(2순위)으로 안내받은 상태. 면접은 APP 운영 위주로 진행되고 레거시 웹 운영도 보조로 나올 수 있다고 보고 준비.

## 면접장 들어가기 전 5초 원칙

1. **모든 문장의 주어는 "나"**. "회사가", "팀이" 아니라 "저는 ~을 판단해서 ~했습니다."
2. **경험은 아래 2개 프로젝트로만 수렴.** 이것저것 늘어놓지 말 것.
3. **숫자(39%, 1천만원, 2,394건)를 말했으면 끝까지 설명할 수 있어야 한다.**
4. **모르는 질문 = "모릅니다"로 끝내지 않기.** 아는 범위 말하고, 연결하고, 필요하면 되묻는다.
5. **마지막 "질문 있으신가요?"는 평가 항목.** 절대 "없습니다"로 끝내지 않는다.

## 나를 설명하는 한 문장

> **"증상만 지우지 않고, 원인을 구조적으로 없애는 사람."**

자기소개/장단점/지원동기/대표경험 전부 이 한 문장으로 수렴하게 말할 것.

### 자기소개 (45초~1분 버전 — 웹뷰 성능 개선 하나로 끝까지 채움)
"저는 박준철입니다. (주)홈초이스에서 OTT 서비스 '오초이스' 앱을 Flutter와 Spring Boot로 개발/운영했는데, 그중 웹뷰 성능을 개선했던 경험으로 저를 소개하고 싶습니다.

오초이스는 콘텐츠 탐색 화면을 웹뷰로 띄우는 구조였는데, 첫 화면이 뜨는 데 시간이 오래 걸린다는 피드백이 반복됐습니다. 감으로 판단하지 않고 구간별 소요 시간을 측정해서 원인을 세 가지로 좁혔습니다.

첫째는 렌더링 방식이었습니다. 서버 렌더링(SSR) 응답을 기다리는 동안 사용자가 빈 화면을 보고 있어야 했는데, 클라이언트 렌더링(CSR)으로 바꾸고 그 사이에 스켈레톤 UI를 먼저 보여줬습니다. 둘째는 이미지였습니다. 화면에 안 보이는 이미지까지 한꺼번에 불러오고 있어서, Lazy Load로 필요한 시점에만 불러오게 하고 CDN 앞단에 리사이저를 붙여 이미지 용량을 1/10 수준으로 줄였습니다. 셋째는 캐시였습니다. 꺼져 있던 웹뷰 네이티브 캐시와 CDN 캐시를 함께 켜서 재방문 로딩을 줄이고, 오리진 서버로 가는 트래픽도 줄였습니다.

이 세 가지를 하나씩 순서대로 적용하면서 매번 같은 조건에서 여러 번 반복 측정해 기여도를 따로 확인했고, 최종적으로 첫 화면 표시 속도를 39% 단축했고 인프라 비용도 연 1천만 원 절감했습니다. 저는 문제를 만나면 증상만 지우지 않고, 이렇게 원인을 끝까지 쪼개서 구조적으로 없애는 방식으로 일합니다."

**30초로 줄여야 하면 이 버전**: "저는 홈초이스에서 OTT 앱 '오초이스'의 웹뷰 성능을 개선했던 경험으로 저를 소개하고 싶습니다. 첫 화면 로딩이 느리다는 피드백을 구간별로 측정해 원인을 세 가지로 좁혔습니다. 서버 렌더링을 클라이언트 렌더링으로 바꿔 스켈레톤 UI를 먼저 보여줬고, 이미지는 Lazy Load와 CDN 리사이저로 용량을 1/10로 줄였고, 웹뷰와 CDN 캐시를 함께 켰습니다. 그 결과 첫 화면 속도를 39% 단축하고 인프라 비용도 연 1천만 원 절감했습니다. 증상만 지우지 않고 원인을 구조적으로 없애는 게 제 방식입니다."

## 5가지 질문 — 답이 서로 이어지는지 최종 점검 (어긋나면 면접관에게 "빈칸"으로 읽힘)

| 왜 이 회사여야 하는가 | 나비엔 스마트 앱처럼 실물 기기(보일러)와 연결된 서비스는 안정성이 곧 안전이라, 제가 우선순위로 두는 "구조적 해결"이 그대로 필요한 곳이다 |
| 나는 무엇을 잘하는 사람인가 | 요청받은 것만 하지 않고 비효율/장애의 원인을 끝까지 추적해서 재발 안 하게 만드는 사람 |
| 입사하면 무엇을 하고 싶은가 | 앱 배포/운영을 먼저 안정적으로 맡고, 이후 API 연동/데이터 검증 쪽으로 역할을 넓히고 싶다 |
| 3년 뒤 어디 있고 싶은가 | 나비엔 스마트 앱과 코맥스 연동 플랫폼까지, 여러 서비스를 안정적으로 책임지는 사람이 되어 있고 싶다 |

**주의**: "성장 기회가 좋아서", "연봉/복지가", "회사가 커서" 같은 조건형 답은 절대 하지 말 것 — 조건이 사라지면 떠날 이유가 된다. 위 표처럼 전부 "방향"으로 답할 것. ("큰 회사여서"가 아니라 "내 역량을 더 큰 규모에서 검증하고 싶어서"로 방향을 바꿔서 말하는 이유가 이것.)

### Q. 왜 이직/이동하려고 하시나요? (전체 답변)
"홈초이스와 아우토크립트는 인원이 많지 않은 회사라, 기획부터 개발, 배포, 운영까지 전 과정을 제가 직접 다뤄볼 수 있었습니다. 문제가 생기면 어디서부터 봐야 하는지 스스로 판단하고 끝까지 해결하는 감각을 그 과정에서 키웠고, 지금도 이게 제 가장 큰 자산이라고 생각합니다.

다만 혼자 또는 소수 인원이 전체를 감당하다 보니, 제가 만든 구조가 더 많은 사용자와 더 복잡한 시스템 앞에서도 여전히 통하는지는 검증해볼 기회가 없었습니다. 그래서 이제는 매출 1조 원 규모에 매장 1,000여 개, 여러 브랜드와 시스템이 얽혀 있는 경동나비엔 같은 조직에서, 제가 쌓아온 '원인을 구조적으로 없애는' 방식이 더 큰 규모에서도 통하는지 시험해보고 싶습니다."

## 0. 먼저 알아둘 회사/제품 사실 (질문에 답할 때 근거로 쓸 것)
*(2026-09-17 웹 검색으로 사실관계 검증 완료 — 출처는 문서 맨 아래 참고)*

- 경동나비엔은 보일러/온수기 앱 **"나비엔 스마트"**를 서비스 중. 보일러 전원, 난방모드/온도, 예약난방, 온수온도를 Wi-Fi/LTE로 원격제어. KT 기가지니 홈IoT와도 연동 이력 있음.
- **2025년 12월 코맥스(1968년 설립, 국내 최초 인터폰 전문기업, 월패드/도어락/CCTV 등 스마트홈 기기 제조, 100여 개국 수출)를 328억원에 인수 발표.** 인수 절차는 2026년 2월 말까지 마무리 예정이었고, 지금(2026년 하반기) 시점에는 완료된 상태로 보는 게 맞음.
- **중요(정정): 코맥스 브랜드·판매/생산 체계·고객서비스는 인수 후에도 기존과 동일하게 유지**한다고 공식적으로 밝혀짐. 즉 "나비엔 앱과 코맥스 앱을 하나로 합친다"가 아니라, **보일러/온수기/제습환기청정기/나비엔 매직과 코맥스의 월패드/도어락/CCTV를 연동해서 온도·습도·공기질·보안까지 통합 관리하는 "생활환경 허브" 플랫폼을 만드는 방향**에 가깝다고 보는 게 더 정확함. 면접에서 "두 앱을 합친다"고 단정적으로 말하지 말고 "연동/통합 플랫폼" 뉘앙스로 답할 것.
- 보일러 시장 점유율/선호도에서 **귀뚜라미와 경쟁**(오차범위 내 1~2위), 린나이/대성쎌틱이 그 뒤. 해외매출 비중 72%, 미국 시장이 특히 큼.
- 2024년 SK매직 조리기기 사업 인수 → "나비엔 매직" 브랜드 런칭.
- 2024.12 한국MS와 클라우드/AI 도입 협약, M365 Copilot/RPA로 업무 자동화 추진 중(이건 AX 직무 쪽 배경이라 APP/웹 운영 면접에서 직접 나올 가능성은 낮지만, "지원 배경"을 물으면 언급 가능).
- **한계 고지**: 채용 특화 면접 후기는 못 찾았지만, 대신 나비엔 스마트 앱의 실제 사용자 리뷰를 전수 조사함 — 아래 "0-2" 참고. 면접 후기보다 실전에서 훨씬 쓸모 있는 자료.

## 0-2. 나비엔 스마트 앱 실사용자 리뷰에서 확인한 문제점 (2026-09-18 앱스토어/구글플레이 조사)

**경동나비엔 앱 목록**: 나비엔 스마트(메인 IoT 제어, App Store 평점 4.4/3,800명 평가), 나비엔 하우스(구매여정 통합 — 제품탐색~상담~AS), 나비엔 스마트톡 보일러(구버전, 2024.09.02 서비스 종료), 경동나비엔/원 고객서비스관리, NaviLink, Navien Smart Plus, KD파트너포탈(대리점용), Navien Heat Pump, 나비엔 멀티킷. 코맥스 앱(월패드 제어)도 별도 존재.

**나비엔 스마트 앱 리뷰에서 반복적으로 나오는 문제**:
1. 앱 업데이트 후 기존에 연결돼 있던 기기(온수매트 등) 연동이 끊기고, 재등록을 시도해도 블루투스를 켜도 "주변에 기기 없음"으로 나와 등록 자체가 안 됨
2. 온도 표시가 계속 0도로 뜨는 센서 값 동기화 오류 (개발사가 숙면매트 블루투스 모델 결함을 인정하고 개선판 배포를 약속함)
3. 업데이트 후 기기가 임의로 대기모드로 전환되는 문제 — "자다가 추워서 깨고 감기 달고 산다"는 실사용자 피해 사례
4. 신버전은 1계정만 기기에 연결 가능, 구버전은 가족 여러 명이 공유 가능했던 기능이 축소됨(기능 후퇴)
5. 예약 꺼짐 설정 시 등록된 기기가 앱 목록에서 사라지는 버그
6. **개발사 대응 패턴**: "환경마다 다르다, 고객센터(1588-1144)로 문의해달라"는 답변으로 끝나는 경우가 많음 — 근본 원인 설명이나 구조적 해결책 제시 없이 개별 문의로 유도
7. (참고) 코맥스 월패드 앱은 무한 버퍼링, 앱 실행 안 됨, "일시적으로 사용할 수 없음" 메시지 등 안정성 문제 다수 보고

**면접에서 쓸 방향**: 6번 패턴(고객센터로 넘기는 대응)은 내가 계속 강조해온 "증상만 지우지 않고 구조적으로 해결한다"는 태도와 정확히 대비되는 사례. "리뷰 보셨나요?" 질문이 나오면 이 지점을 짚으면서 방화벽 장애 근본해결/FAQ 챗봇 이중화 경험과 자연스럽게 연결할 것.

## 0-1. 핵심 프로젝트 2개 (모든 답변은 이 두 프로젝트로 수렴시킬 것)

면접에서 나오는 대부분의 질문은 아래 두 프로젝트 중 하나로 답한다. 이것저것 짧게 언급하는 대신 이 두 개를 깊게 판다.

**프로젝트 1. 오초이스 OTT 앱 (헬로tv+딜라이브 통합, iOS/Android 앱 운영)**
- App Store/Google Play 직접 배포, 인증서·프로비저닝 프로파일 관리, 심사 반려(권한 사유 부족) 대응
- 서로 다른 DRM(NCG DRM vs Multi DRM)을 쓰던 두 파트너사 앱을 단일 플레이어 인터페이스로 추상화해 마이그레이션
- **웹뷰 성능 개선**: SSR→CSR 전환(스켈레톤 UI 적용) + 이미지 다이어트(Lazy Load, CDN 앞단 리사이저로 용량 1/10) + 캐시 정책 개선(웹뷰 네이티브 캐시 + CDN 캐시 활성화, 오리진 트래픽 감소로 인프라 비용 연 약 1천만 원 절감) → 첫 화면 표시 속도 39% 단축
- Spring Boot REST API + Quartz 배치(5분 주기 6개 잡)로 콘텐츠 발행~배포 자동화
- 로드밸런싱 환경 방화벽 정책 변경으로 반복된 통신 장애 → 프록시 IP를 Elastic IP로 고정해 재발 방지

**프로젝트 2. 아우토크립트 IT 자산관리 시스템 (Java/Spring Boot/React, 직접 기획·개발·운영)**
- 엑셀에 흩어져 있던 조직도/IT 자산 현황을 웹 시스템으로 전환, 실사용 데이터 2,394건(인원 306명/자산 1,471건) 이관
- 온보딩 절차를 4단계 마법사 UI로 표준화(정보입력→기기지급→계정생성→완료), SW 라이선스 만료 자동 경고
- 헬프데스크 MS Form 접수를 Power Automate+Teams Webhook으로 자동 알림, 전송 실패 건은 별도 상태로 재처리
- Docker+Render API로 배포 자동화, 그 과정의 CORS 오류·데이터 이관 누락을 직접 원인 추적해 해결

### 6단계로 완전히 소화하기 (예상질문 100개보다 이게 중요 — 막힘없이 말할 수 있어야 함)

**프로젝트 1 — 웹뷰 성능 개선**
1. 문제: 오초이스 웹뷰 첫 화면 로딩이 느리다는 피드백
2. 내 몫: 구간별 소요 시간 측정, 원인 세 가지 분리, 개선 설계/적용 전부 직접 수행
3. 대안: (a) 서버 스펙 증설로 응답 자체를 빠르게 — 비용은 즉시 늘지만 근본 원인(불필요한 렌더 대기/이미지 용량/캐시 미사용)은 그대로 남음. (b) SSR→CSR+스켈레톤/이미지 다이어트/캐시 정책 세 가지를 구조적으로 개선 — 작업량은 크지만 원인 자체를 없앰
4. 선택 이유: 서버를 키우는 건 증상 완화일 뿐이라, 시간이 걸려도 원인 세 가지를 각각 없애는 (b)를 택함

6. 다시 한다면: 세 가지를 순서대로 배포하며 기여도를 따로 측정했는데, 처음부터 각 단계에 측정 지점을 심어두면 중간에 반복 측정하는 수고를 줄일 수 있었을 것

**프로젝트 2 — 자산관리 시스템 자체 개발**
1. 문제: 조직도/IT 자산이 담당자 개인 엑셀 여러 개에 흩어져, 담당자 교체 시 인수인계가 부실해짐 (아무도 요청하지 않음)
2. 내 몫: 문제 발견부터 기획/개발/이관까지 전부 직접 수행
3. 대안: (a) 엑셀 서식 표준화 — 당장 빠르지만 반년 뒤 또 흩어질 게 뻔함. (b) Java/Spring Boot/React 웹 시스템으로 전환 — 초기 비용 크지만 근본 해결
4. 선택 이유: 반복될 게 뻔한 문제를 알면서 방치할 수 없어서 (b)를 택함
5. 결과: 실사용 데이터 2,394건(306명/1,471건) 이관, 온보딩 4단계 표준화, 라이선스 만료 자동 경고
6. 다시 한다면: 저 혼자만 아는 시스템이 아니라, 다른 담당자도 확장할 수 있게 설계 문서를 처음부터 같이 만들어뒀을 것

## 1. 회사/제품에 대한 이해를 묻는 질문 (범용 HR 질문 대신 이 섹션이 핵심)

### Q. 나비엔 스마트 앱을 써보셨거나 살펴보셨나요? IoT 디바이스 제어 앱이 일반 서비스 앱과 다르게 신경 써야 할 부분이 뭐라고 생각하시나요?
써봤습니다. 일반 콘텐츠 앱은 화면에 뭔가 안 뜨면 새로고침하면 그만이지만, 보일러 원격제어는 "앱에서 누른 명령이 실제로 보일러에 전달됐는지"를 신뢰할 수 있어야 한다는 점이 다르다고 생각합니다. 저는 OTT 앱에서 서버-클라이언트 상태가 어긋나는 문제를 겪어봤는데, 그때는 영상이 안 나오는 정도였지만 보일러는 "껐다고 표시되는데 실제로는 켜져 있는" 상황이 안전 문제로 이어질 수 있습니다. 그래서 명령을 보낸 뒤 디바이스의 실제 응답을 받아 상태를 다시 동기화하는 확인 절차, 그리고 응답이 일정 시간 안에 안 오면 사용자에게 "적용 확인 중"처럼 불확실한 상태를 숨기지 않고 보여주는 설계가 중요하다고 봅니다.

**예상 꼬리질문 1. 그럼 폴링(Polling) 방식과 Push(MQTT/WebSocket) 방식 중 어떤 걸 쓰시겠어요?**
IoT 디바이스는 배터리/네트워크 환경이 다양하니 무조건 Push가 정답은 아니라고 생각합니다. 다만 보일러처럼 상시 전원이 연결된 기기는 실시간성이 중요한 온도/상태 변경에는 Push(MQTT) 쪽이 유리하고, 대신 연결이 끊겼을 때를 대비해 일정 주기로 폴링해서 상태를 재확인하는 걸 같이 두는 하이브리드 구조가 안전할 것 같습니다. 저도 WebSocket으로 서버-클라이언트 실시간 동기화를 구현해본 적이 있는데, 그때도 연결이 끊긴 걸 감지 못해서 클라이언트가 낡은 상태를 계속 보여주는 문제가 있었고, 하트비트로 연결 상태를 주기적으로 확인하는 방식으로 보완했습니다.

**예상 꼬리질문 2. 앱과 디바이스 사이 통신이 방화벽이나 NAT 때문에 막히면 어떻게 대응하시겠어요?**
제가 오초이스에서 겪었던 문제와 방향이 비슷하다고 생각합니다. 로드밸런싱 환경에서 방화벽 정책이 바뀔 때마다 서버 간 통신이 끊기는 장애가 있었는데, 그때 재연결로 덮지 않고 프록시 서버의 IP를 Elastic IP로 고정해서 방화벽 정책 자체에 흔들리지 않는 구조로 바꿨습니다. IoT 디바이스도 가정마다 공유기/방화벽 환경이 제각각이라, 디바이스 쪽에서 아웃바운드로 먼저 연결을 열어 서버와 세션을 유지하는 방식(디바이스가 클라이언트처럼 서버에 접속)이 인바운드로 뚫는 것보다 훨씬 안정적일 거라고 생각합니다.

### Q. 경동나비엔이 코맥스를 인수했는데, 앱 개발/운영 관점에서 어떤 이슈가 예상되나요?
기사들을 보면 코맥스는 브랜드와 판매·생산 체계, 고객서비스를 기존처럼 유지한다고 나와 있어서, 완전히 하나의 앱으로 합친다기보다는 두 브랜드의 기기를 하나의 통합 플랫폼에서 연동하는 방향에 가까울 거라고 예상합니다. 그래도 서로 다른 회사가 각자 만든 디바이스와 프로토콜을 하나의 시스템에서 다뤄야 한다는 본질은 같아서, 제가 헬로tv와 딜라이브 두 파트너사 앱을 오초이스 하나로 통합했던 마이그레이션 경험과 방향이 비슷하다고 생각합니다. 그때 가장 큰 문제는 두 서비스가 DRM 방식이 아예 달랐던 거였는데(NCG DRM vs Multi DRM), 각 방식을 하나씩 다 이해하려 하지 않고 DRM 방식을 추상화한 단일 플레이어 인터페이스를 만들어서 그 뒤에 서로 다른 구현을 숨겼습니다. 나비엔과 코맥스의 기기를 연동할 때도, 보일러 제어 프로토콜과 월패드/도어락 프로토콜을 하나의 공통 디바이스 제어 인터페이스로 추상화하고, 그 아래에서 각 브랜드별 통신 방식을 감추는 구조가 필요할 것 같습니다.

**예상 꼬리질문. 나비엔 스마트 앱에 코맥스 기기 제어까지 합치는 것과, 완전히 새로운 통합 허브 앱을 별도로 만드는 것 중 어느 쪽을 택하시겠어요?**
코맥스 브랜드와 앱을 그대로 유지하기로 한 상황이라, 저라면 기존 두 앱을 갑자기 하나로 합치기보다는 각 앱은 유지한 채로 WebView/모듈 형태로 서로의 기능 일부를 하나씩 노출하는 방식을 먼저 검토하겠습니다. 제가 오초이스로 마이그레이션할 때도 React+WebView JS Bridge로 화면을 분리해서, 앱을 다시 배포하지 않고도 콘텐츠를 즉시 반영할 수 있는 구조를 만들었는데, 브랜드가 유지되는 상황일수록 이런 식으로 리스크를 줄이면서 연동 범위를 단계적으로 넓혀가는 게 안전하다고 봅니다.

### Q. 보일러 시장은 귀뚜라미/린나이 등과 경쟁이 치열한데, 서비스 앱이 경쟁사 대비 어떤 부분에서 차별화될 수 있다고 생각하시나요?
보일러 자체의 하드웨어 성능 차이는 제가 판단할 영역이 아니지만, 앱 경험은 확실히 차별화 포인트가 될 수 있다고 생각합니다. 특히 경동나비엔은 코맥스 인수로 월패드/도어락/CCTV까지 연동하려는 방향이라, "보일러 하나만 제어하는 앱"이 아니라 "집 전체 생활환경을 하나의 플랫폼에서 관리"하는 경험을 얼마나 매끄럽게 만드느냐가 경쟁사 대비 차별점이 될 것 같습니다. 저는 OTT 앱에서 여러 서비스를 하나로 통합하면서 로딩 속도를 39% 단축한 경험이 있는데, 여러 기능이 한 앱에 몰릴수록 반응 속도와 안정성이 더 중요해진다는 걸 체감했습니다.

### Q. 나비엔 스마트 앱 리뷰를 보신 적 있나요? 개선하고 싶은 부분이 있다면?
네, 준비하면서 앱스토어와 구글플레이 리뷰를 살펴봤습니다. 반복적으로 나오는 패턴이 몇 가지 있었는데, 업데이트 이후 기존에 연결돼 있던 기기가 재등록이 안 되거나, 예약 꺼짐 설정을 하면 등록된 기기가 목록에서 사라지는 증상이었습니다. 그리고 개발사 답변을 보면 "환경마다 달라서 그렇다, 고객센터로 문의해달라"로 끝나는 경우가 많더라고요.

저는 이게 원인을 구조적으로 짚지 못하고 있다는 신호라고 봤습니다. 기기 연동이 끊기는 문제라면, 사용자가 재등록을 다시 시도하게 하는 것보다, 업데이트 시점에 기존 기기의 페어링 정보가 그대로 유지되는지를 먼저 검증하는 마이그레이션 단계가 있었어야 한다고 생각합니다. 제가 아우토크립트에서 FAQ 챗봇을 만들 때도 비슷한 판단을 한 적이 있는데, 챗봇 하나가 죽으면 접수 전체가 끊기는 구조였어서, 챗봇을 고도화하기보다 챗봇이 죽어도 접수 자체는 안 끊기는 이중화 구조로 바꿨습니다. IoT 기기 제어도 비슷하게, 업데이트가 되어도 기존 연결이 깨지지 않는 방향으로 먼저 설계하고, 그래도 깨졌을 때는 사용자가 왜 안 되는지 이해할 수 있는 메시지를 보여주는 게 필요하다고 생각합니다.

**꼬리질문. 리뷰만 보고 실제 원인을 안다고 확신할 수 있나요?**
확신하지는 않습니다. 리뷰는 증상만 보여주기 때문에, 실제로 입사하면 로그나 크래시 리포트, 기기 펌웨어 버전별 재현 조건을 먼저 확인해야 한다고 생각합니다. 다만 리뷰에서 반복되는 패턴(업데이트 후 연동 끊김, 개별 문의로 유도되는 대응)만으로도 지금 이 앱이 문제를 어떤 방식으로 다루고 있는지는 짐작할 수 있었고, 입사하면 이런 반복 패턴부터 구조적으로 짚어보고 싶습니다.

## 2. APP 운영 — 기술 질문 (꼬리질문 체인)

### Q1. Android/iOS 앱 배포 경험을 구체적으로 말씀해주세요.
오초이스 앱을 App Store와 Google Play 양쪽에 직접 배포했습니다. iOS는 Apple Developer 인증서와 프로비저닝 프로파일을 관리하고 TestFlight로 먼저 배포했습니다. Android는 Keystore 서명과 ProGuard 설정을 직접 했습니다. "권한 사용 목적 설명 부족"으로 심사 반려를 받은 적이 있는데, Info.plist의 권한 사유 문구를 구체적으로 보강해서 재제출해 통과시켰습니다.

**꼬리질문 1. 인증서가 만료되기 직전에 발견했다면 어떻게 대응하시겠어요?**
서비스 운영 중 실제로 겪을 수 있는 상황이라, 저는 인증서 만료일을 캘린더로 별도 관리하고 만료 30일 전에 알림이 오도록 해뒀습니다. 만약 정말 임박해서 발견했다면, 우선 신규 인증서/프로비저닝 프로파일을 발급받아 배포를 준비하는 동시에, 기존 앱이 만료로 강제 종료되는 최악의 상황을 대비해 서버 쪽에서 점검 공지를 띄울 수 있는 구조를 미리 마련해두는 게 안전하다고 생각합니다.

**꼬리질문 2. 심사 반려 사유가 애매해서 원인을 특정하기 어려울 때는 어떻게 접근하시겠어요?**
리젝 사유 문구만 보고 짐작하지 않고, 최근 변경한 항목(권한 요청, 새로 추가한 API, 스크린샷/메타데이터)을 하나씩 되짚어서 어떤 변경이 반려 시점과 맞물리는지 좁혀갑니다. 애매하면 Apple/Google 리졸루션 센터로 구체적인 재현 방법을 요청해서 근거를 확보한 다음 대응합니다.

### Q2. 앱 버전 관리(강제 업데이트/선택 업데이트)는 어떻게 설계하셨나요?
서버에서 최소 지원 버전을 내려주고, 클라이언트 버전이 그보다 낮으면 강제 업데이트, 아니면 선택 업데이트로 안내하는 구조를 직접 만들었습니다.

**꼬리질문 1. 강제 업데이트 팝업이 뜨는 도중에 서버가 응답을 못 주면 사용자는 앱을 아예 못 쓰게 되는데, 이 리스크는 어떻게 관리하시겠어요?**
버전 체크 API가 실패했을 때 무조건 강제 업데이트로 막아버리면 서버 장애가 곧바로 앱 전체 장애로 번지기 때문에, 버전 체크 실패 시에는 기본값을 "통과(앱 정상 진입)"로 두고 별도로 장애를 모니터링하는 쪽을 택하겠습니다. 강제 차단은 명확히 낮은 버전이라는 응답을 받았을 때만 적용하는 게 안전합니다.

**꼬리질문 2. 나비엔처럼 IoT 디바이스와 통신하는 앱이라면, 구버전 앱을 쓰는 사용자의 디바이스 제어 명령이 신버전 서버 프로토콜과 안 맞을 수 있는데 어떻게 대응하시겠어요?**
디바이스 제어 프로토콜은 사용자 안전과 직결되기 때문에, 화면 UI보다 훨씬 보수적으로 하위 호환을 관리해야 한다고 생각합니다. 프로토콜 자체에 버전 필드를 두고 서버가 클라이언트 버전에 맞는 프로토콜로 응답하도록 하거나, 아예 제어 관련 변경은 강제 업데이트 대상으로 분류해서 오래된 프로토콜로 디바이스에 잘못된 명령이 가는 상황 자체를 막는 게 맞다고 봅니다.

### Q3. API 연동 경험과, 앱에서 API 응답이 이상할 때 원인을 어떻게 좁혀나가시나요?
Spring Boot로 앱과 연동되는 REST API 서버를 직접 개발했고, Quartz 배치로 5분 주기 잡 6개를 구성해 콘텐츠 발행부터 배포까지 자동화했습니다. 응답이 이상하면 클라이언트 로그, 네트워크 구간, 서버 로그 순서로 좁혀갑니다.

**꼬리질문. 그 셋 중 어디서부터 보는 게 맞다고 생각하시고, 그 순서를 정한 기준은 뭔가요?**
저는 클라이언트부터 봅니다. 앱이 보낸 요청 자체가 잘못됐는지(파라미터 누락, 캐시된 낡은 토큰 등)를 먼저 배제해야, 그다음 네트워크 문제인지 서버 문제인지로 범위를 좁힐 수 있기 때문입니다. 실제로 로드밸런싱 통신 장애 때도 처음엔 서버 로그부터 봤다가 시간을 허비했는데, 나중에 보니 클라이언트가 오래된 IP로 계속 요청을 보내고 있었던 게 원인이었습니다. 그 경험 이후로는 항상 클라이언트 쪽 요청 내용을 먼저 확인하는 순서로 바꿨습니다.

### Q4. 모바일 앱(웹뷰) 성능 개선 경험을 구체적으로 말씀해주세요.
감으로 판단하지 않고 수치로 확인합니다. 오초이스 웹뷰에서 첫 화면 로딩이 느리다는 피드백을 받고, Chrome 개발자도구로 구간별 소요 시간을 측정해 병목을 세 가지로 좁혔고, 하나씩 순서대로 개선했습니다.

첫째, 아키텍처 전환입니다. 초기 응답 속도를 높이려고 서버 사이드 렌더링(SSR)에서 클라이언트 사이드 렌더링(CSR)으로 바꿨고, 그 덕분에 서버 렌더링이 끝나길 기다리는 대신 화면이 뜨기 전에 스켈레톤 UI를 먼저 보여줄 수 있게 됐습니다. 둘째, 이미지 다이어트입니다. 화면에 안 보이는 이미지는 Lazy Load로 나중에 불러오게 하고, CDN 앞단에 이미지 리사이저를 붙여 이미지 용량을 1/10 수준으로 줄였습니다. 셋째, 캐시 정책 개선입니다. 꺼져 있던 웹뷰의 네이티브 캐시와 CDN 캐시 설정을 함께 활성화해서 재방문 시 로딩을 빠르게 했고, 오리진 서버로 가는 트래픽이 줄면서 인프라 비용도 연간 약 1천만 원 절감했습니다. 이 세 가지를 합쳐서 첫 화면 표시 속도를 39% 단축했습니다.

**꼬리질문 1. "39% 단축"과 "연 1천만 원 절감"이라는 수치는 어떻게 확인하셨고, 세 가지 개선 중 뭐가 가장 크게 기여했는지는 어떻게 나눠서 보셨나요?**
세 가지를 한 번에 적용하지 않고 SSR→CSR 전환, 이미지 다이어트, 캐시 정책 순서로 하나씩 배포하면서 매 단계마다 동일한 네트워크·기기 조건에서 여러 차례 반복 측정해 기여도를 따로 기록했습니다. 우연한 네트워크 변수를 배제하려고 한두 번이 아니라 여러 번 측정한 값의 분포로 비교했습니다. 인프라 비용 절감은 캐시 활성화 전후로 CDN 대시보드의 캐시 히트율과 오리진 트래픽 청구 내역을 비교해서 확인했습니다.

**꼬리질문 3. CDN 캐시와 웹뷰 네이티브 캐시는 역할이 어떻게 다른가요?**
웹뷰 네이티브 캐시는 사용자 기기 안에 저장돼서 같은 사용자가 재방문할 때 네트워크 요청 자체를 건너뛰게 해주고, CDN 캐시는 우리 오리진 서버 앞에서 여러 사용자의 요청을 대신 받아서 오리진으로 가는 트래픽 자체를 줄여줍니다. 그래서 첫 방문 사용자의 체감 속도는 CDN 캐시가, 재방문 사용자의 체감 속도는 웹뷰 캐시가 더 크게 기여한다고 보고 두 가지를 같이 켰습니다.

**꼬리질문 2. SSR을 CSR로 바꾸면 초기 진입 시 빈 화면이 보일 수 있는데 이건 어떻게 고려하셨나요?**
이 화면은 앱 안에서 열리는 웹뷰라 SEO는 고려 대상이 아니었고, 오히려 서버 렌더링 응답을 기다리는 동안 사용자가 아무것도 못 보는 게 더 큰 문제였습니다. 그래서 CSR로 바꾸면서 빈 화면 대신 스켈레톤 UI를 먼저 보여주는 방식으로 "화면이 비어 보이는" 체감 문제를 해결했습니다.

**꼬리질문 4. 구간별 소요 시간은 구체적으로 어떻게 측정하셨나요?**
안드로이드/iOS 웹뷰라 `chrome://inspect`로 원격 디버깅을 연결해서, 데스크톱 Chrome 개발자도구를 웹뷰에 그대로 붙여서 봤습니다. Network 탭의 워터폴로 요청별 DNS/연결/TTFB(첫 바이트까지 걸리는 시간)/다운로드 구간이 각각 얼마나 걸리는지 나눠서 봤고, Performance 탭 레코딩으로 First Paint와 First Contentful Paint 시점을 확인했습니다. 이미지 로드 완료 시점이나 캐시 히트 여부처럼 커스텀 구간은 코드에 `performance.mark()`/`performance.measure()`를 심어서 콘솔로 따로 확인했습니다. 이렇게 모은 수치로 전체 로딩 시간에서 어느 구간이 가장 큰 비중을 차지하는지 순서를 매겨서, 렌더링 방식/이미지/캐시 세 가지로 원인을 좁혔습니다.

## 3. 레거시 웹 운영 — 기술 질문 (보조 대비)

### Q1. Java 기반 사내 업무 시스템 운영 경험이 있나요?
아우토크립트에서 엑셀로 흩어진 조직도/IT 자산 현황을 Java/Spring Boot/React 기반 시스템으로 직접 개발해 운영하고 있습니다. 온보딩 절차를 4단계 마법사 UI로 표준화하고, SW 라이선스 만료 자동 경고 기능도 붙였습니다.

**꼬리질문. 레거시 시스템을 새로 만들지 않고 "운영"만 해야 하는 상황이라면, 처음부터 다시 만드는 것과 뭐가 다르다고 생각하시나요?**
새로 만들 때는 제가 설계 기준을 정할 수 있지만, 운영은 이미 다른 사람이 내린 설계 판단을 먼저 이해하고 존중하는 데서 시작해야 한다고 생각합니다. 아우토크립트 자산관리 시스템도 온보딩 절차를 마법사 UI로 바꾸기 전에, 기존 담당자가 엑셀로 관리하던 순서(정보입력→기기지급→계정생성→완료)를 먼저 그대로 따라가며 왜 그 순서였는지 이해한 다음에 화면으로 옮겼는데, 레거시 화면도 왜 그렇게 짜여 있는지 먼저 파악한 다음에 손대는 순서로 접근하겠습니다.

### Q2. WebSquare나 JSP를 다뤄본 적이 있나요?
직접 실무로 써본 적은 아직 없습니다. 다만 Java 기반 서버사이드 렌더링 구조와 Spring MVC의 뷰 계층을 다뤄본 경험이 있어서, JSP가 서버에서 HTML에 자바 코드를 넣어 동적으로 화면을 생성하는 방식이라는 것과, WebSquare가 전자정부 표준프레임워크 계열의 국산 UI 프레임워크라는 것은 개념적으로 이해하고 있습니다.

**꼬리질문. 경험 없는 기술을 실무에 바로 투입돼서 써야 한다면, 첫 1~2주는 어떻게 접근하시겠어요?**
문서보다 기존 화면 코드를 먼저 읽겠습니다. 제가 오초이스에서 웹뷰와 네이티브 앱 사이 JS Bridge 통신 구조를 처음 설계할 때도, 이론부터 공부하기보다 화면 하나를 직접 붙여서 postMessage가 오가는 걸 눈으로 확인하며 구조를 익혔는데, 그렇게 동작하는 걸 직접 만져보는 방식이 저한테는 가장 빠릅니다. WebSquare/JSP도 기존 화면 하나를 잡아서 요청이 들어와 화면이 그려지기까지의 흐름을 코드로 따라가보는 것부터 시작하겠습니다.

### Q3. SQL은 어느 정도 다뤄보셨나요?
MySQL과 DynamoDB로 서비스 데이터를 직접 처리했고, 아우토크립트 자산관리 시스템에서 306명, 1,471건 규모의 데이터를 조회/이관하는 쿼리를 직접 작성했습니다.

**꼬리질문 1. 조회 쿼리가 느려지면 어떤 순서로 원인을 찾으시나요?**
먼저 실행 계획(EXPLAIN)을 봐서 풀 스캔이 일어나는지 확인하고, 인덱스가 없거나 조건절이 인덱스를 못 타는 구조인지 봅니다. 그다음 조인이 많다면 꼭 필요한 컬럼만 가져오는지, N+1처럼 반복 쿼리가 발생하는 구조는 아닌지 확인합니다.

**꼬리질문 2. 인덱스를 무조건 많이 걸면 좋은 거 아닌가요?**
아닙니다. 인덱스는 조회는 빠르게 해주지만 쓰기(INSERT/UPDATE) 시마다 인덱스도 같이 갱신해야 해서 쓰기 성능은 떨어집니다. 그래서 자주 조회되는 컬럼 위주로 최소한만 걸고, 쓰기가 잦은 테이블일수록 더 신중하게 판단해야 한다고 생각합니다.

## 4. CS 기본기 (신입/주니어 기술면접 공통)

### Q. REST API를 설계할 때 어떤 원칙을 지키시나요?
자원(Resource) 단위로 URI를 설계하고, 행위는 HTTP 메서드(GET/POST/PUT/DELETE)로 표현합니다. 예를 들어 "사용자를 삭제한다"를 `/deleteUser`처럼 URL에 동사를 넣지 않고 `DELETE /users/{id}`로 표현하는 식입니다. 상태 코드도 200/201/400/404/500처럼 의미에 맞게 구분해서 클라이언트가 응답 코드만 보고도 상황을 판단할 수 있게 합니다.

### Q. Spring에서 트랜잭션은 어떻게 관리하시나요?
`@Transactional`로 서비스 계층에서 트랜잭션 경계를 관리합니다. 여러 테이블에 걸친 작업 중간에 하나라도 실패하면 전체가 롤백되도록 해서 데이터 정합성이 깨지지 않게 합니다.

**꼬리질문. 트랜잭션 안에서 외부 API를 호출하면 어떤 문제가 생길 수 있나요?**
외부 API 응답이 느리면 그동안 DB 커넥션을 계속 붙잡고 있어서 커넥션 풀이 고갈될 수 있고, 외부 호출이 실패했을 때 이미 커밋된 것처럼 보이는 정합성 문제도 생길 수 있습니다. 그래서 외부 API 호출은 트랜잭션 밖으로 빼거나, 실패 시 재처리할 수 있는 별도 구조(상태값 + 재처리 API)로 분리하는 게 안전하다고 생각합니다. 실제로 아우토크립트 헬프데스크 자동화에서 Teams Webhook 연동을 만들 때도 전송 성공/실패 상태를 별도로 관리하고, 실패 건만 재처리하는 구조로 분리했습니다.

### Q. 동시에 같은 데이터를 여러 요청이 수정하려고 하면 어떻게 처리하시나요?
낙관적 락(버전 컬럼 비교)과 비관적 락(SELECT FOR UPDATE) 중 상황에 맞게 고릅니다. 충돌이 드물게 일어나는 경우라면 낙관적 락으로 충분하고, 충돌이 자주 예상되는 재고/결제 같은 데이터는 비관적 락으로 확실히 막는 편이 낫다고 생각합니다.

## 4-1. AI 활용 질문 (나올 확률 높음 — 원래 AX 지원자였기 때문)

### Q. AI 도구를 실무에 어떻게 활용하시나요? / AI보다 본인이 더 잘하는 건 뭔가요?
Claude Code나 Codex로 코드/문서 초안을 빠르게 뽑고, **제가 보증할 수 있는 범위와 아닌 범위를 나눠서** 검증합니다. FAQ 챗봇을 AI로 만들 때, 기본적인 질문-답변 매칭 구조는 AI가 잘 만들었지만 "관리자가 퇴사하거나 서버 장애가 나면 이 구조가 어떻게 깨지는가"는 AI가 먼저 짚어주지 않았습니다. 그 부분은 제가 직접 판단해서 이중화 구조로 다시 설계해달라고 요청했습니다.

자산관리 시스템 만들 때도 AI가 뽑은 코드 초안에서 CORS 오류나 데이터 이관 중 항목 누락이 있었는데, 그건 로그를 직접 찍어보며 원인을 좁혀서 제가 고쳤습니다. **AI가 만든 결과물을 그대로 쓰지 않고, 실패하는 조건을 제가 먼저 의심해보고 깨뜨려보는 게 제 역할**이라고 생각합니다.

## 5. 인성/상황 질문 (압박 후속질문 포함)

### Q. 단점은 무엇인가요?
원인을 찾기 시작하면 끝을 봐야 직성이 풀리는 편입니다. 방화벽 장애처럼 큰 문제는 이 성향 덕에 잘 잡는데, 사소한 이슈에도 똑같은 태도로 덤비면 시간이 아깝다는 걸 최근에 알았습니다. **(개선)** 지금은 이슈가 들어오면 먼저 "이게 지금 끝까지 파고들 문제인가"를 판단하고, 아니라면 시간을 정해두고 그 안에서만 봅니다.

### Q. 팀원과 의견이 부딪힌 경험이 있나요?
*(실제 사례로 답변 준비 필요 — 헬로tv/딜라이브 마이그레이션처럼 팀 4인 프로젝트에서 있었던 구체적 상황을 하나 골라, 문제 상황 → 내가 검토한 대안 2가지 이상 → 그중 하나를 선택한 이유 → 결과 순서로 정리해둘 것. 알려주시면 이 문서에 채워넣겠습니다.)*

**예상 꼬리질문 1. 그때 팀원이 끝까지 본인 생각에 반대했다면 어떻게 하셨을 것 같나요?**
**예상 꼬리질문 2. 지금 돌아보면 그 판단이 최선이었다고 생각하시나요, 아쉬운 부분은 없나요?**

### Q. 가장 힘들었던 경험과 극복 방법은?
로드밸런싱 환경에서 방화벽 정책이 바뀔 때마다 통신이 끊기는 장애가 반복됐던 상황입니다. 재연결로 덮으면 당장은 넘어갈 수 있었지만, 며칠 뒤 같은 문제가 또 터질 걸 알면서 방치할 수는 없었습니다. 로그를 구간별로 뜯어보며 프록시 서버 IP 변경 이력을 확인했고, IP를 Elastic IP로 고정하는 구조로 인프라를 재구성해서 재발을 막았습니다.

**꼬리질문. 만약 그 방법으로도 재발했다면 다음 대안은 뭐였을까요?**
Elastic IP 고정이 실패했다면, 방화벽 정책 변경 시점에 자동으로 감지해서 알림을 주는 모니터링을 먼저 붙이고, 근본 원인이 방화벽 쪽 정책 관리 프로세스 자체에 있다고 보고 방화벽을 관리하는 팀과 정책 변경 시 사전 공유하는 프로세스를 만드는 쪽으로 접근했을 것 같습니다.

### Q. 낯선 기술을 빠르게 익혀야 했던 경험은?
오초이스 웹뷰 성능 이슈를 맡았을 때, 그전까지는 서버 사이드 렌더링만 다뤄봤지 클라이언트 사이드 렌더링으로 아키텍처 자체를 바꿔본 적은 없었습니다. 문서로 이론부터 정리하기보다 화면 하나를 먼저 CSR로 바꿔보고 스켈레톤 UI가 실제로 어떻게 동작하는지 눈으로 확인한 다음, 나머지 화면으로 범위를 넓혀갔습니다. 처음 접하는 영역이라도 실제로 동작하는 작은 예시부터 만들어보면서 익히는 방식이 저한테 맞습니다.

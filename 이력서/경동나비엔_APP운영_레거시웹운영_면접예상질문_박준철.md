# 경동나비엔 면접 준비 — APP 운영(1순위) / 레거시 웹 운영(2순위)

AI/자동화(AX)로 지원했으나 서류전형에서 APP 운영(1순위), 레거시 웹 운영(2순위)으로 안내받은 상태. 면접은 APP 운영 위주로 진행되고 레거시 웹 운영도 보조로 나올 수 있다고 보고 준비.

## 면접장 들어가기 전 5초 원칙

1. **모든 문장의 주어는 "나"**. "회사가", "팀이" 아니라 "저는 ~을 판단해서 ~했습니다."
2. **경험은 아래 2개 프로젝트로만 수렴.** 이것저것 늘어놓지 말 것.
3. **숫자(FCP 39%, LCP 32.8%, 2,394건)를 말했으면 끝까지 설명할 수 있어야 한다.**
4. **모르는 질문 = "모릅니다"로 끝내지 않기.** 아는 범위 말하고, 연결하고, 필요하면 되묻는다.
5. **마지막 "질문 있으신가요?"는 평가 항목.** 절대 "없습니다"로 끝내지 않는다.

## 나를 설명하는 한 문장

> **"증상만 지우지 않고, 원인을 구조적으로 없애는 사람."**

자기소개/장단점/지원동기/대표경험 전부 이 한 문장으로 수렴하게 말할 것.

### 자기소개 (45초~1분 버전 — 웹뷰 성능 개선 하나로 끝까지 채움)
"저는 박준철입니다. (주)홈초이스에서 OTT 서비스 '오초이스' 앱을 Flutter와 Spring Boot로 개발/운영했는데, 그중 웹뷰 성능을 개선했던 경험으로 저를 소개하고 싶습니다.

오초이스는 콘텐츠 탐색 화면을 웹뷰로 띄우는 구조였는데, 첫 화면이 뜨는 데 시간이 오래 걸린다는 피드백이 반복됐습니다. 감으로 판단하지 않고 구간별 소요 시간을 측정해서 원인을 두 가지로 좁혔습니다.

첫째는 렌더링 방식이었습니다. 서버가 여러 백엔드 API를 순차로 호출한 뒤에야 HTML을 한 번에 내려주는 구조라, 스트리밍 없이 그 호출이 다 끝날 때까지 사용자는 아무 인디케이터도 없이 완전히 빈 화면을 보고 있어야 했습니다. 그래서 클라이언트 렌더링(CSR)으로 바꾸면서, CDN에 스켈레톤 UI만 담긴 가벼운 HTML을 올려두고 그 파일부터 먼저 받아와 화면 뼈대를 즉시 띄운 다음, 데이터는 API 응답이 오는 대로 비동기로 채우는 구조로 바꿨습니다. 둘째는 이미지였습니다. 화면에 안 보이는 이미지까지 한꺼번에 불러오고 있어서, Lazy Load로 필요한 시점에만 불러오게 하고 CDN 앞단에 리사이저를 붙여 이미지 용량을 1/10 수준으로 줄였습니다.

이 두 가지를 하나씩 순서대로 적용하면서 매번 같은 조건에서 여러 번 반복 측정해 기여도를 따로 확인했고, 최종적으로 화면이 비어 보이지 않게 되는 시점(FCP)을 39% 앞당겼습니다. 여기에 더해 LCP에 필요한 API 호출 우선순위를 앞당기고 덜 중요한 작업은 뒤로 미뤄서, 실제 콘텐츠가 자리 잡는 시점(LCP)도 32.8% 개선했습니다. 저는 문제를 만나면 증상만 지우지 않고, 이렇게 원인을 끝까지 쪼개서 구조적으로 없애는 방식으로 일합니다."

**30초로 줄여야 하면 이 버전**: "저는 홈초이스에서 OTT 앱 '오초이스'의 웹뷰 성능을 개선했던 경험으로 저를 소개하고 싶습니다. 첫 화면 로딩이 느리다는 피드백을 구간별로 측정해 원인을 두 가지로 좁혔습니다. 서버가 여러 API를 순차 호출한 뒤 HTML을 한번에 내려주던 구조를 클라이언트 렌더링으로 바꾸고, CDN에 올려둔 가벼운 스켈레톤 HTML을 먼저 받아와 화면 뼈대부터 즉시 보여줬고, 이미지는 Lazy Load와 CDN 리사이저로 용량을 1/10로 줄였습니다. 여기에 LCP에 필요한 API 호출 우선순위도 앞당겼습니다. 그 결과 FCP를 39% 단축하고 LCP도 32.8% 개선했습니다. 증상만 지우지 않고 원인을 구조적으로 없애는 게 제 방식입니다."

## 5가지 질문 — 답이 서로 이어지는지 최종 점검 (어긋나면 면접관에게 "빈칸"으로 읽힘)

하나의 정체성("증상만 지우지 않고, 원인을 구조적으로 없앤다")을 축으로 다섯 질문이 한 줄로 이어지게 만듦. 각 답은 앞 답을 전제로 해야 함 — 하나씩 순서대로 읽었을 때 "그래서"로 연결되는지 확인할 것.

| 순서 | 질문 | 답 (앞 답과의 연결) |
|---|---|---|
| ① | 나는 무엇을 잘하는 사람인가 | 요청받은 것만 하지 않고, 비효율/장애의 원인을 구조적으로 추적해서 재발하지 않게 만드는 사람 |
| ② | 왜 옮기려고 하는가 | (①을 증명해온 무대의 한계) 작은 회사에서 이 방식을 계속 증명해왔지만, 제가 만든 구조가 틀려도 최악의 경우는 서비스 장애 정도였다. 이제는 더 많은 사용자와, 실수했을 때 결과가 훨씬 무거운 환경에서 같은 방식이 통하는지 검증하고 싶다 |
| ③ | 왜 이 회사여야 하는가 | (②의 "무거운 결과"가 바로 이곳) 나비엔 스마트 앱처럼 실물 기기(보일러)와 연결된 서비스는 임시조치가 곧바로 안전 문제로 이어질 수 있는 곳이라, 내가 우선순위로 두는 "구조적 해결"이 다른 곳보다 더 필요하다 |
| ④ | 입사하면 무엇을 하고 싶은가 | (③에서 검증을 시작할 자리) 앱 배포/운영에서 반복되는 문제부터 구조적으로 없애 신뢰성을 먼저 쌓고, 같은 방식을 API 연동/데이터 검증처럼 사용자 안전과 더 가까운 영역으로 넓히고 싶다 |
| ⑤ | 3년 뒤 어디 있고 싶은가 | (④가 넓어진 결과) 앱 하나의 안정성을 넘어서, 나비엔 스마트와 코맥스 연동처럼 여러 실물 기기가 엮이는 지점까지 같은 방식으로 신뢰를 책임지는 사람이 되어 있고 싶다 |

**주의**: "성장 기회가 좋아서", "연봉/복지가", "회사가 커서" 같은 조건형 답은 절대 하지 말 것 — 조건이 사라지면 떠날 이유가 된다. ("큰 회사여서"가 아니라 "내 역량을 더 큰 규모에서 검증하고 싶어서"로 방향을 바꿔서 말하는 이유가 이것.) 실제 면접에서는 표에 있는 순서(①②③④⑤)가 아니라 면접관이 질문하는 순서대로 답하면 되는데, 그때도 머릿속으로는 항상 ①의 정체성에서 출발해서 답을 이어갈 것.

### Q. 왜 이직/이동하려고 하시나요? (전체 답변)
"홈초이스와 아우토크립트는 인원이 많지 않은 회사라, 기획부터 개발, 배포, 운영까지 전 과정을 제가 직접 다뤄볼 수 있었습니다. 문제가 생기면 어디서부터 봐야 하는지 스스로 판단하고 끝까지 해결하는 감각을 그 과정에서 키웠고, 지금도 이게 제 가장 큰 자산이라고 생각합니다.

다만 그 방식을 증명해온 무대에는 한계가 있었습니다. 제가 만든 구조가 틀려도 최악의 경우는 서비스 장애 정도였습니다. 이제는 더 많은 사용자, 그리고 실수했을 때 결과가 훨씬 무거운 환경에서도 같은 방식이 통하는지 검증해보고 싶습니다. 경동나비엔처럼 보일러/온수기같이 실물 기기와 연결된 서비스는 임시조치가 곧바로 안전 문제로 이어질 수 있는 만큼, 제가 우선순위로 두는 '원인을 구조적으로 없애는' 방식이 다른 어떤 곳보다 필요한 자리라고 생각했습니다."

### Q. 왜 이 회사여야 하나요? (독립 질문으로 나올 때, 이직 이유와 별도로 답하는 버전)
"저는 요청받은 것만 하지 않고, 문제의 원인을 구조적으로 없애는 걸 우선순위로 두는 사람입니다. 이 방식은 어떤 서비스에나 도움이 되지만, 특히 나비엔 스마트 앱처럼 보일러 같은 실물 기기와 연결된 서비스에서는 필수에 가깝다고 생각합니다. 일반 서비스 앱은 임시조치로 덮어도 다음날 다시 고치면 되지만, 보일러 원격제어는 '껐다고 표시되는데 실제로는 켜져 있는' 상황이 안전 문제로 바로 이어질 수 있으니까요. 제가 가장 중요하게 여기는 방식이 가장 필요한 자리라고 판단해서 지원했습니다."

1. **재등록/재페어링 실패가 서로 다른 앱 2곳에서 동일하게 나타남**: 나비엔 스마트는 "업데이트 후 온수매트 연동 끊김, 블루투스 켜도 주변에 기기 없음"으로 재등록 불가. 나비엔 로비패스는 "틈만 나면 먹통, 재등록해도 문열기 버튼이 안 먹힘". 앱은 다르지만 증상 패턴(연결 유실 → 재등록 시도 → 실패)이 같음.
2. 온도 표시가 계속 0도로 뜨는 센서 값 동기화 오류 (개발사가 숙면매트 블루투스 모델 결함을 인정, 개선판 배포 약속)
3. 업데이트 후 기기가 임의로 대기모드로 전환 — "자다가 추워서 깨고 감기 달고 산다"는 실사용자 피해 사례
4. 신버전은 1계정만 기기에 연결 가능, 구버전은 가족 공유가 가능했던 기능이 축소(기능 후퇴)
5. 예약 꺼짐 설정 시 등록된 기기가 앱 목록에서 사라지는 버그
6. 로비패스는 iOS에서 자동 문열림이 안 되고 앱을 직접 열어야 하는 문제가 있는데, **이건 iOS 자체의 한계가 아닐 가능성이 큼**. 홈패스/패스미/현대건설 스마트폰키 같은 경쟁 공동현관 앱들은 iOS에서도 앱을 아예 실행 안 해도(심지어 종료된 상태에서도) 자동으로 문을 여는 걸 실제로 구현하고 있음 — iOS가 iBeacon 리전 모니터링(Always 위치 권한 + CLBeaconRegion)이라는, 앱이 꺼져 있어도 근처에 오면 시스템이 앱을 깨워주는 정식 메커니즘을 제공하기 때문. 로비패스가 이걸 안 쓰고 있다면 플랫폼 제약이 아니라 구현 방식의 차이일 가능성이 높음(면접에서 "이건 OS 탓"이라고 단정하지 말 것 — 경쟁사 사례를 근거로 "구현 선택의 문제일 수 있다"고 말할 것)
7. **개발사 대응 패턴**: "환경마다 다르다, 고객센터(1588-1144)로 문의해달라"로 끝나는 경우가 많음 — 근본 원인 설명이나 구조적 해결책 제시 없이 개별 문의로 유도
8. (참고) 코맥스 월패드 앱은 무한 버퍼링, 앱 실행 안 됨, "일시적으로 사용할 수 없음" 메시지 등 안정성 문제 다수 보고

**면접에서 쓸 방향**: 1번(서로 다른 앱 2개에서 동일 패턴)이 가장 강력한 근거. "개별 앱의 버그"가 아니라 "블루투스/IoT 페어링을 다루는 공통 방식 자체에 개선 여지가 있어 보인다"는 수준으로 말하면, 리뷰 몇 개 읽고 성급히 결론내리는 게 아니라 구조적으로 패턴을 읽는 사람으로 보임. 7번(고객센터로 넘기는 대응)은 내가 계속 강조해온 "증상만 지우지 않고 구조적으로 해결한다"는 태도와 정확히 대비되는 사례이므로, 방화벽 장애 근본해결/FAQ 챗봇 이중화 경험과 자연스럽게 연결할 것.

## 0-1. 핵심 프로젝트 2개 (모든 답변은 이 두 프로젝트로 수렴시킬 것)

면접에서 나오는 대부분의 질문은 아래 두 프로젝트 중 하나로 답한다. 이것저것 짧게 언급하는 대신 이 두 개를 깊게 판다.

**프로젝트 1. 오초이스 OTT 앱 (헬로tv+딜라이브 통합, iOS/Android 앱 운영)**
- App Store/Google Play 직접 배포, 인증서·프로비저닝 프로파일 관리, 심사 반려(권한 사유 부족) 대응
- 서로 다른 DRM(NCG DRM vs Multi DRM)을 쓰던 두 파트너사 앱을 단일 플레이어 인터페이스로 추상화해 마이그레이션
- **웹뷰 성능 개선**: 순차 백엔드 API 호출 뒤 일괄 응답하던 SSR→CSR 전환(CDN 스켈레톤 셸 적용) + 이미지 다이어트(Lazy Load, CDN 앞단 리사이저로 용량 1/10) + LCP 관련 API 호출 우선순위 조정 → **FCP 39% 단축, LCP 32.8% 개선**
- Spring Boot REST API + Quartz 배치(5분 주기 6개 잡)로 콘텐츠 발행~배포 자동화
- 로드밸런싱 환경 방화벽 정책 변경으로 반복된 통신 장애 → 프록시 IP를 Elastic IP로 고정해 재발 방지

**프로젝트 2. 아우토크립트 IT 자산관리 시스템 (Java/Spring Boot/React, 직접 기획·개발·운영)**
- 엑셀에 흩어져 있던 조직도/IT 자산 현황을 웹 시스템으로 전환, 실사용 데이터 2,394건(인원 306명/자산 1,471건) 이관
- 온보딩 절차를 4단계 마법사 UI로 표준화(정보입력→기기지급→계정생성→완료), SW 라이선스 만료 자동 경고
- 헬프데스크 MS Form 접수를 Power Automate+Teams Webhook으로 자동 알림, 전송 실패 건은 별도 상태로 재처리
- Docker+Render API로 배포 자동화, 그 과정의 CORS 오류·데이터 이관 누락을 직접 원인 추적해 해결

### 6단계로 완전히 소화하기 (예상질문 100개보다 이게 중요 — 막힘없이 말할 수 있어야 함)

**프로젝트 1 — 웹뷰 성능 개선**
1. 문제: 오초이스 웹뷰 첫 화면 로딩이 느리다는 피드백
2. 내 몫: 구간별 소요 시간 측정, 원인 두 가지 분리, 개선 설계/적용 전부 직접 수행
3. 대안: (a) 서버 스펙 증설이나 백엔드 API 응답 자체를 빠르게 튜닝 — 비용/시간은 즉시 늘지만, 순차 호출 구조 자체(스트리밍 없이 다 모은 뒤 응답)와 이미지 용량 문제는 그대로 남음. (b) SSR→CSR+스켈레톤/이미지 다이어트 두 가지를 구조적으로 개선 — 작업량은 크지만 원인 자체를 없앰
4. 선택 이유: 서버를 키우는 건 증상 완화일 뿐이라, 시간이 걸려도 원인 두 가지를 각각 없애는 (b)를 택함
5. 결과: FCP(스켈레톤 표시 시점) 39% 단축, LCP(실제 콘텐츠 표시 시점, API 우선순위 조정으로 개선) 32.8% 개선
6. 다시 한다면: 두 가지를 순서대로 배포하며 기여도를 따로 측정했는데, 처음부터 각 단계에 측정 지점을 심어두면 중간에 반복 측정하는 수고를 줄일 수 있었을 것

**프로젝트 2 — 자산관리 시스템 자체 개발**
1. 문제: 조직도/IT 자산이 담당자 개인 엑셀 여러 개에 흩어져, 담당자 교체 시 인수인계가 부실해짐 (아무도 요청하지 않음)
2. 내 몫: 문제 발견부터 기획/개발/이관까지 전부 직접 수행
3. 대안: (a) 엑셀 서식 표준화 — 당장 빠르지만 반년 뒤 또 흩어질 게 뻔함. (b) Java/Spring Boot/React 웹 시스템으로 전환 — 초기 비용 크지만 근본 해결
4. 선택 이유: 반복될 게 뻔한 문제를 알면서 방치할 수 없어서 (b)를 택함
5. 결과: 실사용 데이터 2,394건(306명/1,471건) 이관, 온보딩 4단계 표준화, 라이선스 만료 자동 경고
6. 다시 한다면: 저 혼자만 아는 시스템이 아니라, 다른 담당자도 확장할 수 있게 설계 문서를 처음부터 같이 만들어뒀을 것

## 1. 회사/제품에 대한 이해를 묻는 질문 (범용 HR 질문 대신 이 섹션이 핵심)

### Q. 나비엔 스마트 앱을 써보셨거나 살펴보셨나요? IoT 디바이스 제어 앱이 일반 서비스 앱과 다르게 신경 써야 할 부분이 뭐라고 생각하시나요?
써봤습니다. 일반 콘텐츠 앱은 화면에 뭔가 안 뜨면 새로고침하면 그만이지만, 보일러 원격제어는 "앱에서 누른 명령이 실제로 보일러에 전달됐는지"를 신뢰할 수 있어야 한다는 점이 다르다고 생각합니다. 저는 OTT 앱에서 서버-클라이언트 상태가 어긋나는 문제를 겪어봤는데, 그때는 영상이 안 나오는 정도였지만 보일러는 "껐다고 표시되는데 실제로는 켜져 있는" 상황이 안전 문제로 이어질 수 있습니다. 그래서 명령을 보낸 뒤 디바이스의 실제 응답을 받아 상태를 다시 동기화하는 확인 절차, 그리고 응답이 일정 시간 안에 안 오면 사용자에게 "적용 확인 중"처럼 불확실한 상태를 숨기지 않고 보여주는 설계가 중요하다고 봅니다.

**예상 꼬리질문 1. 그럼 폴링(Polling) 방식과 Push(MQTT/WebSocket) 방식 중 어떤 걸 쓰시겠어요?**
IoT 디바이스는 배터리/네트워크 환경이 다양하니 무조건 Push가 정답은 아니라고 생각합니다. 다만 보일러처럼 상시 전원이 연결된 기기는 실시간성이 중요한 온도/상태 변경에는 Push(MQTT) 쪽이 유리하고, 대신 연결이 끊겼을 때를 대비해 일정 주기로 폴링해서 상태를 재확인하는 걸 같이 두는 하이브리드 구조가 안전할 것 같습니다. 저도 WebSocket으로 서버-클라이언트 실시간 동기화를 구현해본 적이 있는데, 그때도 연결이 끊긴 걸 감지 못해서 클라이언트가 낡은 상태를 계속 보여주는 문제가 있었고, 하트비트로 연결 상태를 주기적으로 확인하는 방식으로 보완했습니다.

**예상 꼬리질문 2. 앱과 디바이스 사이 통신이 방화벽이나 NAT 때문에 막히면 어떻게 대응하시겠어요?**
제가 오초이스에서 겪었던 문제와 방향이 비슷하다고 생각합니다. 로드밸런싱 환경에서 방화벽 정책이 바뀔 때마다 서버 간 통신이 끊기는 장애가 있었는데, 그때 재연결로 덮지 않고 프록시 서버의 IP를 Elastic IP로 고정해서 방화벽 정책 자체에 흔들리지 않는 구조로 바꿨습니다. IoT 디바이스도 가정마다 공유기/방화벽 환경이 제각각이라, 디바이스 쪽에서 아웃바운드로 먼저 연결을 열어 서버와 세션을 유지하는 방식(디바이스가 클라이언트처럼 서버에 접속)이 인바운드로 뚫는 것보다 훨씬 안정적일 거라고 생각합니다.

### Q. 경동나비엔이 코맥스를 인수했는데, 앱 개발/운영 관점에서 어떤 이슈가 예상되나요?
기사들을 보면 코맥스는 브랜드와 판매·생산 체계, 고객서비스를 기존처럼 유지한다고 나와 있어서, 완전히 하나의 앱으로 합친다기보다는 두 브랜드의 기기를 하나의 통합 플랫폼에서 연동하는 방향에 가까울 거라고 예상합니다. 그래도 서로 다른 회사가 각자 만든 디바이스와 프로토콜을 하나의 시스템에서 다뤄야 한다는 본질은 같아서, 제가 헬로tv와 딜라이브 두 파트너사 앱을 오초이스 하나로 통합했던 마이그레이션 경험과 방향이 비슷하다고 생각합니다. 그때 가장 큰 문제는 두 서비스가 DRM 방식이 아예 달랐던 거였는데(NCG DRM vs Multi DRM), 각 방식을 하나씩 다 이해하려 하지 않고 DRM 방식을 추상화한 단일 플레이어 인터페이스를 만들어서 그 뒤에 서로 다른 구현을 숨겼습니다. 나비엔과 코맥스의 기기를 연동할 때도, 보일러 제어 프로토콜과 월패드/도어락 프로토콜을 하나의 공통 디바이스 제어 인터페이스로 추상화하고, 그 아래에서 각 브랜드별 통신 방식을 감추는 구조가 필요할 것 같습니다.

**예상 꼬리질문. 나비엔 스마트 앱에 코맥스 기기 제어까지 합치는 것과, 완전히 새로운 통합 허브 앱을 별도로 만드는 것 중 어느 쪽을 택하시겠어요?**
코맥스 브랜드와 앱을 그대로 유지하기로 한 상황이라, 저라면 기존 두 앱을 갑자기 하나로 합치기보다는 각 앱은 유지한 채로 WebView/모듈 형태로 서로의 기능 일부를 하나씩 노출하는 방식을 먼저 검토하겠습니다. 제가 오초이스로 마이그레이션할 때도 React+WebView JS Bridge로 화면을 분리해서, 앱을 다시 배포하지 않고도 콘텐츠를 즉시 반영할 수 있는 구조를 만들었는데, 브랜드가 유지되는 상황일수록 이런 식으로 리스크를 줄이면서 연동 범위를 단계적으로 넓혀가는 게 안전하다고 봅니다.

### Q. 보일러 시장은 귀뚜라미/린나이 등과 경쟁이 치열한데, 서비스 앱이 경쟁사 대비 어떤 부분에서 차별화될 수 있다고 생각하시나요?
보일러 자체의 하드웨어 성능 차이는 제가 판단할 영역이 아니지만, 앱 경험은 확실히 차별화 포인트가 될 수 있다고 생각합니다. 특히 경동나비엔은 코맥스 인수로 월패드/도어락/CCTV까지 연동하려는 방향이라, "보일러 하나만 제어하는 앱"이 아니라 "집 전체 생활환경을 하나의 플랫폼에서 관리"하는 경험을 얼마나 매끄럽게 만드느냐가 경쟁사 대비 차별점이 될 것 같습니다. 저는 OTT 앱에서 여러 서비스를 하나로 통합하면서 로딩 속도를 39% 단축한 경험이 있는데, 여러 기능이 한 앱에 몰릴수록 반응 속도와 안정성이 더 중요해진다는 걸 체감했습니다.

### Q. 나비엔 스마트 앱 리뷰를 보신 적 있나요? 개선하고 싶은 부분이 있다면?
네, 준비하면서 귀사 명의로 나온 앱들을 앱스토어/구글플레이에서 찾아봤는데, 나비엔 스마트 하나가 아니라 로비패스, 스마트홈(월패드), 에어원처럼 15개가 넘는 포트폴리오였습니다. 그중 나비엔 스마트와 로비패스 리뷰를 자세히 봤는데, 흥미로운 점이 있었습니다. 나비엔 스마트는 "업데이트 후 기기 재등록이 안 된다"는 리뷰가 많았고, 로비패스는 "틈만 나면 먹통이고 재등록해도 문열기가 안 된다"는 리뷰가 많았습니다. 서로 다른 앱인데 "연결이 끊기고 재등록도 안 된다"는 증상이 똑같이 나온다는 게 눈에 띄었습니다. 그리고 개발사 답변을 보면 "환경마다 달라서 그렇다, 고객센터로 문의해달라"로 끝나는 경우가 많더라고요.

저는 이게 서로 다른 앱에서 우연히 겹친 게 아니라, 블루투스/IoT 기기를 페어링하고 재연결하는 공통 방식 자체에 개선 여지가 있다는 신호일 수 있다고 봤습니다. 기기 연동이 끊기는 문제라면, 사용자가 재등록을 다시 시도하게 하는 것보다, 업데이트 시점에 기존 기기의 페어링 정보가 그대로 유지되는지를 먼저 검증하는 마이그레이션 단계가 있었어야 한다고 생각합니다. 제가 아우토크립트에서 FAQ 챗봇을 만들 때도 비슷한 판단을 한 적이 있는데, 챗봇 하나가 죽으면 접수 전체가 끊기는 구조였어서, 챗봇을 고도화하기보다 챗봇이 죽어도 접수 자체는 안 끊기는 이중화 구조로 바꿨습니다. IoT 기기 제어도 비슷하게, 업데이트가 되어도 기존 연결이 깨지지 않는 방향으로 먼저 설계하고, 그래도 깨졌을 때는 사용자가 왜 안 되는지 이해할 수 있는 메시지를 보여주는 게 필요하다고 생각합니다.

**꼬리질문. 리뷰만 보고 실제 원인을 안다고 확신할 수 있나요?**
확신하지는 않습니다. 리뷰는 증상만 보여주기 때문에, 실제로 입사하면 로그나 크래시 리포트, 기기 펌웨어 버전별 재현 조건을 먼저 확인해야 한다고 생각합니다. 다만 리뷰에서 반복되는 패턴(업데이트 후 연동 끊김, 개별 문의로 유도되는 대응)만으로도 지금 이 앱이 문제를 어떤 방식으로 다루고 있는지는 짐작할 수 있었고, 입사하면 이런 반복 패턴부터 구조적으로 짚어보고 싶습니다.

**먼저 용어 정리** *(모르는 분야면 이것부터 — 답변에 쓴 단어들이 실제로 무슨 뜻인지 모르면 꼬리질문에서 바로 막힘)*
- **BLE(Bluetooth Low Energy)**: 일반 블루투스보다 전력을 훨씬 적게 쓰는 블루투스 규격. 배터리로 오래 버텨야 하는 IoT 기기(온수매트 등)에 널리 쓰임.
- **UUID(Universally Unique Identifier)**: 전 세계에서 절대 안 겹치게 만든 고유 식별 번호. BLE에서는 "이 온수매트"를 다른 모든 블루투스 기기와 구분하는 이름표라고 생각하면 됨.
- **스캔(Scan)**: 앱이 주변 블루투스 기기가 보내는 신호(광고)를 찾아 목록으로 모으는 과정. 리뷰의 "주변에 기기가 없다"는 이 단계에서 아예 신호를 못 잡았다는 뜻.
- **연결(Connect)/GATT**: 스캔으로 찾은 기기와 실제로 데이터를 주고받기 위해 붙는 과정. GATT는 "온도 값은 이 주소로, 전원 제어는 저 주소로" 하는 식으로 기기와 앱이 데이터를 주고받을 때 쓰는 공통 규격(문법)임.
- **페어링/본딩(Pairing/Bonding)**: 기기와 앱이 서로 신뢰를 확인하고 암호화 키를 주고받는 과정(페어링), 그 결과(키)를 저장해서 다음엔 다시 확인 안 해도 되게 만드는 것(본딩).
- **breadcrumb**: 직역하면 "빵 부스러기". 헨젤과 그레텔이 길을 잃지 않으려고 빵 부스러기를 흘려놓은 것처럼, 앱이 동작하는 과정에서 "여기까지는 왔다"는 흔적을 단계마다 로그로 남겨두는 것. 나중에 이 흔적을 따라가면 어느 단계에서 멈췄는지 알 수 있음.
- **HCI(Host Controller Interface) 스누프 로그**: 스마트폰의 블루투스 칩이 실제로 공중에 주고받는 저수준 무선 신호(패킷)를 그대로 기록한 로그. 앱 코드보다 훨씬 아래 단계에서 "진짜 전파가 오갔는지"를 볼 수 있음. Android 개발자 옵션에서 켤 수 있음.
- **PacketLogger / bluetoothd**: iOS/Mac에서 HCI 스누프 로그에 해당하는 도구/대상. `bluetoothd`는 iOS/macOS에서 블루투스를 담당하는 백그라운드 프로세스(데몬) 이름이고, PacketLogger는 애플이 개발자용으로 제공하는 그 무선 패킷 캡처 도구.
- **CBCentralManagerDelegate**: iOS에서 블루투스를 쓸 때 사용하는 Core Bluetooth 프레임워크의 콜백 모음. "기기를 발견했다", "연결 성공/실패했다" 같은 이벤트가 생길 때마다 여기 정의된 각 메서드가 호출됨.
- **상관관계 분석**: 여러 로그(앱 버전, OS 버전, 기기 모델)를 모아놓고 "어떤 조건에서 실패가 유독 몰려 있는지"를 찾는 분석 방법. 원인을 바로 보는 게 아니라, 실패와 특정 조건이 같이 나타나는 패턴으로 범위를 좁혀가는 방식.

**꼬리질문. 그럼 로그로는 구체적으로 어떻게 원인을 좁히시겠어요?** *(1위 문제인 "기기 연결/재등록 실패"를 예로)*
단계별로 어디서 끊기는지부터 나눠서 보겠습니다. 기기 연결은 보통 스캔 → 기기 발견 → 연결 시도 → GATT 연결 성공 → 페어링/본딩 완료, 이렇게 여러 단계를 거치는데, 지금은 "주변에 기기 없음"이라는 증상 하나로 뭉뚱그려 보이지만 실제로는 이 중 어느 단계에서 끊기는지에 따라 원인이 완전히 다릅니다.

**클라이언트 로그**: 안드로이드는 `BluetoothLeScanner`/`BluetoothGatt` 콜백을, iOS는 `CBCentralManagerDelegate`의 `didDiscover`/`didConnect`/`didFailToConnect`/`didDisconnectPeripheral` 콜백을 단계마다 breadcrumb으로 남기겠습니다. 여기에 로컬에 저장된 기기 정보(기기 UUID, 마지막 페어링 시각, 저장 시점의 앱 버전)도 같이 남겨서, "스캔에서 기기가 아예 안 잡히는 것"과 "스캔엔 잡히는데 연결이 실패하는 것"과 "연결은 되는데 로컬에 저장된 기기 UUID랑 안 맞는 것"을 구분하겠습니다.

**저수준 무선 로그**: 안드로이드는 개발자 옵션의 HCI 스누프 로그(무선으로 실제 나간 advertising/connection 패킷을 캡처), iOS는 Apple의 PacketLogger나 Console.app의 bluetoothd 로그로 실제 무선 레벨에서 기기가 광고 신호를 보내고 있는지, 연결 요청에 응답하는지까지 내려가서 볼 수 있습니다.

**서버 로그**: 기기 등록/재등록 API 요청 payload와 응답, 그리고 기기-계정 매핑 테이블이 앱 업데이트 전후로 실제 바뀌었는지를 이력으로 남기겠습니다.

**상관관계 분석**: 이 로그들을 앱 버전, OS 버전, 기기 모델 기준으로 묶어서, 특정 업데이트 버전 이후에만 몰려 있는지, 특정 안드로이드/iOS 버전에서만 나는지를 먼저 찾겠습니다. 만약 특정 업데이트 시점 이후로 몰려 있다면 그 업데이트의 마이그레이션 로직을, 특정 OS 버전에 몰려 있다면 그 OS의 BLE 정책 변경(권한/백그라운드 제약)을 의심하는 식으로 범위를 좁혀가겠습니다.

**꼬리질문. 그럼 리뷰에 나온 문제들, 구체적으로 어떻게 고치시겠어요?** *(리뷰 패턴별 기술적 가설과 해결 방향 — 실제 원인은 로그를 봐야 확정되므로 "~가 원인일 가능성이 있고, 그렇다면 ~로 접근하겠다"는 가설 형태로 말할 것)*

- **재등록 실패(나비엔 스마트/로비패스 공통)**: BLE는 앱 업데이트 시 로컬에 저장된 기기 페어링 정보(기기 UUID, 서비스 characteristic, 본딩 키)가 스키마 변경으로 유실되거나, iOS/Android가 BLE 기기의 식별자를 세션마다 다르게 주는 경우 "이전에 연결했던 그 기기"라고 인식을 못 할 수 있습니다. 그렇다면 접근은 두 가지입니다. 첫째, DB 스키마 마이그레이션처럼 페어링 정보도 버전을 매겨서, 앱 업데이트 시 구버전 페어링 데이터를 신버전 구조로 명시적으로 이관하는 단계를 둡니다. 둘째, 클라이언트 로컬 상태가 깨지더라도 서버는 "이 계정이 이 기기를 소유하고 있다"는 사실을 알고 있으니, 재등록을 "새 기기 추가"가 아니라 "기존 소유 기기 재연결"로 처리해서 사용자가 처음부터 다시 설정하지 않게 만듭니다. 스캔 방식도 매번 브로드캐스트 스캔에만 의존하지 말고, 알고 있는 기기 ID로 직접 연결을 먼저 시도하고 실패하면 스캔으로 폴백하는 순서로 바꾸겠습니다.

- **온도 0도 표시**: "값이 아직 안 왔다"와 "실제로 0도다"를 구분 못 하는 게 원인일 가능성이 높습니다. 센서 값을 nullable로 다루지 않고 기본값 0으로 초기화해두면, 값이 안 오는 상황과 실측 0도가 화면에서 똑같이 보입니다. 값이 없을 때는 "측정 중"처럼 명시적으로 다른 상태를 보여주고, 실제 값이 와야만 숫자를 렌더링하도록 바꾸겠습니다.

- **업데이트 후 임의 대기모드 전환**: 사용자가 설정해둔 예약/모드 값이 앱 업데이트 시 서버 기본값으로 덮어써지는 마이그레이션 버그일 가능성이 있습니다. 페어링 정보와 마찬가지로 사용자 설정값도 버전 관리하고, 업데이트 전후 값을 비교해서 달라졌으면 사용자에게 먼저 확인받는 절차를 넣겠습니다.

- **신버전 1계정 제한(가족 공유 기능 후퇴)**: 이건 버그가 아니라 설계 자체가 기기:계정을 1:1로 바꾼 결과로 보입니다. 기기-계정 관계를 다시 N:1(소유자+구성원 역할 구분)로 설계하고, 구버전에서 여러 계정이 연결돼 있던 기기는 마이그레이션 시 소유자 1명 + 나머지는 구성원으로 자동 매핑해서 사용자가 권한을 잃었다고 느끼지 않게 하겠습니다.

- **예약 꺼짐 시 기기가 목록에서 사라짐**: 기기 상태(켜짐/꺼짐/오프라인/미등록)를 하나의 값으로 뭉뚱그려서, "꺼짐"을 "연결 안 됨/기기 없음"과 같은 걸로 취급해 리스트에서 걸러버리는 로직 문제일 가능성이 있습니다. 상태를 명확히 분리된 값으로 관리하고, 리스트는 항상 "등록된 기기"를 기준으로 그리고 전원 상태는 별도 배지로만 표시하도록 바꾸겠습니다.

- **로비패스 iOS 백그라운드 자동 문열림 제한**: 처음엔 이게 iOS 자체의 한계라고 생각했는데, 찾아보니 홈패스나 패스미 같은 경쟁 공동현관 앱들은 iOS에서도 앱을 아예 실행하지 않은 상태(심지어 종료된 상태)에서도 자동으로 문을 엽니다. iOS는 **iBeacon 리전 모니터링**이라는 기능을 제공하는데, 이건 앱이 종료되거나 정지된 상태에서도 시스템이 대신 위치/비콘 감지를 계속하다가, 사용자가 등록된 구역에 들어오면 짧은 시간 동안 앱을 다시 깨워서 실행시켜줍니다. 일반 블루투스 스캔은 백그라운드에서 강하게 제한되지만, 이 리전 모니터링은 Always 위치 권한을 받으면 훨씬 자유롭게 동작합니다. 그래서 로비패스가 이 방식을 쓰고 있는지부터 확인하고, 안 쓰고 있다면 일반 BLE 스캔 대신 iBeacon 리전 모니터링 기반으로 다시 구현하는 쪽으로 접근하겠습니다. 이건 OS 탓이 아니라 구현 선택의 문제일 가능성이 크다고 봅니다.

- **"환경마다 다르다"는 CS 대응 패턴**: 이건 기술보다 관측(observability) 문제에 가깝습니다. 크래시/연결실패 로그를 서버로 자동 수집(펌웨어 버전, 마지막 연결 시각, 실패 사유 코드 포함)해두면, CS가 "환경마다 다르다"로 뭉뚱그리지 않고 실제 로그 기반으로 원인을 좁힐 수 있게 됩니다.

## 2. APP 운영 — 기술 질문 (꼬리질문 체인)

### Q1. Android/iOS 앱 배포 경험을 구체적으로 말씀해주세요.
오초이스 앱을 App Store와 Google Play 양쪽에 직접 배포했습니다. iOS는 Apple Developer 인증서와 프로비저닝 프로파일을 관리하고 TestFlight로 먼저 배포했습니다. Android는 Keystore 서명과 ProGuard 설정을 직접 했습니다. "권한 사용 목적 설명 부족"으로 심사 반려를 받은 적이 있는데, Info.plist의 권한 사유 문구를 구체적으로 보강해서 재제출해 통과시켰습니다.

**꼬리질문 1. 인증서가 만료되기 직전에 발견했다면 어떻게 대응하시겠어요?**
서비스 운영 중 실제로 겪을 수 있는 상황이라, 저는 인증서 만료일을 캘린더로 별도 관리하고 만료 30일 전에 알림이 오도록 해뒀습니다. 만약 정말 임박해서 발견했다면, 우선 신규 인증서/프로비저닝 프로파일을 발급받아 배포를 준비하는 동시에, 기존 앱이 만료로 강제 종료되는 최악의 상황을 대비해 서버 쪽에서 점검 공지를 띄울 수 있는 구조를 미리 마련해두는 게 안전하다고 생각합니다.

**꼬리질문 2. 심사 반려 사유가 애매해서 원인을 특정하기 어려울 때는 어떻게 접근하시겠어요?**
리젝 사유 문구만 보고 짐작하지 않고, 최근 변경한 항목(권한 요청, 새로 추가한 API, 스크린샷/메타데이터)을 하나씩 되짚어서 어떤 변경이 반려 시점과 맞물리는지 좁혀갑니다. 애매하면 Apple/Google 리졸루션 센터로 구체적인 재현 방법을 요청해서 근거를 확보한 다음 대응합니다.

### Q2. 앱 버전 관리(강제 업데이트/선택 업데이트)는 어떻게 설계하셨나요?
서버에서 최소 지원 버전을 내려주고, 클라이언트 버전이 그보다 낮으면 강제 업데이트, 아니면 선택 업데이트로 안내하는 구조를 직접 만들었습니다.

**꼬리질문 1. 강제 업데이트 팝업이 뜨는 도중에 서버가 응답을 못 주면 사용자는 앱을 아예 못 쓰게 되는데, 이 리스크는 어떻게 관리하시겠어요?**
버전 체크 API가 실패했을 때 무조건 강제 업데이트로 막아버리면 서버 장애가 곧바로 앱 전체 장애로 번지기 때문에, 버전 체크 실패 시에는 기본값을 "통과(앱 정상 진입)"로 두고 별도로 장애를 모니터링하는 쪽을 택하겠습니다. 강제 차단은 명확히 낮은 버전이라는 응답을 받았을 때만 적용하는 게 안전합니다.

**꼬리질문 2. 나비엔처럼 IoT 디바이스와 통신하는 앱이라면, 구버전 앱을 쓰는 사용자의 디바이스 제어 명령이 신버전 서버 프로토콜과 안 맞을 수 있는데 어떻게 대응하시겠어요?**
디바이스 제어 프로토콜은 사용자 안전과 직결되기 때문에, 화면 UI보다 훨씬 보수적으로 하위 호환을 관리해야 한다고 생각합니다. 프로토콜 자체에 버전 필드를 두고 서버가 클라이언트 버전에 맞는 프로토콜로 응답하도록 하거나, 아예 제어 관련 변경은 강제 업데이트 대상으로 분류해서 오래된 프로토콜로 디바이스에 잘못된 명령이 가는 상황 자체를 막는 게 맞다고 봅니다.

### Q3. API 연동 경험과, 앱에서 API 응답이 이상할 때 원인을 어떻게 좁혀나가시나요?
Spring Boot로 앱과 연동되는 REST API 서버를 직접 개발했고, Quartz 배치로 5분 주기 잡 6개를 구성해 콘텐츠 발행부터 배포까지 자동화했습니다. 응답이 이상하면 클라이언트 로그, 네트워크 구간, 서버 로그 순서로 좁혀갑니다.

**꼬리질문. 그 셋 중 어디서부터 보는 게 맞다고 생각하시고, 그 순서를 정한 기준은 뭔가요?**
저는 클라이언트부터 봅니다. 앱이 보낸 요청 자체가 잘못됐는지(파라미터 누락, 캐시된 낡은 토큰 등)를 먼저 배제해야, 그다음 네트워크 문제인지 서버 문제인지로 범위를 좁힐 수 있기 때문입니다. 실제로 로드밸런싱 통신 장애 때도 처음엔 서버 로그부터 봤다가 시간을 허비했는데, 나중에 보니 클라이언트가 오래된 IP로 계속 요청을 보내고 있었던 게 원인이었습니다. 그 경험 이후로는 항상 클라이언트 쪽 요청 내용을 먼저 확인하는 순서로 바꿨습니다.

### Q4. 모바일 앱(웹뷰) 성능 개선 경험을 구체적으로 말씀해주세요.
감으로 판단하지 않고 수치로 확인합니다. 오초이스 웹뷰에서 첫 화면 로딩이 느리다는 피드백을 받고, Chrome 개발자도구로 구간별 소요 시간을 측정해 병목을 두 가지로 좁혔고, 하나씩 순서대로 개선했습니다.

첫째, 아키텍처 전환입니다. 기존 구조는 서버가 여러 백엔드 API를 순차로 호출해서 데이터를 다 모은 뒤에야 HTML을 한 번에 내려주는 방식이라, 스트리밍 없이 그 호출이 끝날 때까지 사용자는 아무 인디케이터도 없이 완전히 빈 화면을 보고 있어야 했습니다. 그래서 서버 사이드 렌더링(SSR)에서 클라이언트 사이드 렌더링(CSR)으로 바꾸고, CDN에 스켈레톤 UI만 담긴 가벼운 HTML을 올려둬서 그 파일부터 먼저 받아와 화면 뼈대를 즉시 띄운 다음, 데이터는 API 응답이 오는 대로 비동기로 채우는 구조로 바꿨습니다. 둘째, 이미지 다이어트입니다. 화면에 안 보이는 이미지는 Lazy Load로 나중에 불러오게 하고, CDN 앞단에 이미지 리사이저를 붙여 이미지 용량을 1/10 수준으로 줄였습니다. 이 두 가지를 합쳐서 화면이 비어 보이지 않게 되는 시점(FCP)을 39% 단축했고, 여기에 더해 LCP에 필요한 API 호출 우선순위를 앞당기고 덜 중요한 작업은 뒤로 미뤄서 실제 콘텐츠가 자리 잡는 시점(LCP)도 32.8% 개선했습니다.

**꼬리질문 1. "39% 단축"과 "32.8% 개선"이라는 수치는 어떻게 확인하셨고, 각 개선 중 뭐가 가장 크게 기여했는지는 어떻게 나눠서 보셨나요?**
한 번에 다 적용하지 않고 SSR→CSR 전환, 이미지 다이어트, API 호출 우선순위 조정 순서로 하나씩 배포하면서 매 단계마다 동일한 네트워크·기기 조건에서 여러 차례 반복 측정해 기여도를 따로 기록했습니다. 우연한 네트워크 변수를 배제하려고 한두 번이 아니라 여러 번 측정한 값의 분포로 비교했습니다.

**꼬리질문 2. SSR이 원래 더 빠른 게 일반적인데, 왜 반대로 CSR로 바꾸셨나요? 서버 응답 자체를 빠르게 튜닝하는 건 검토 안 하셨나요?**
맞습니다, 보통은 SSR이 초기 콘텐츠를 더 빨리 보여줍니다. 그런데 이 화면의 SSR 구현은 스트리밍 없이, 서버가 상품/콘텐츠 관련 백엔드 API 여러 개를 순차로 호출해서 데이터를 다 모은 다음에야 HTML을 한 번에 내려주는 구조였습니다. 그래서 병목이 JS 다운로드나 실행 시간이 아니라, 그 순차 호출 체인이 끝날 때까지의 TTFB 자체였고, 그 동안 화면엔 로딩 인디케이터조차 없이 완전히 비어 있었습니다. 이 화면은 앱 안에서 열리는 웹뷰라 SEO도 고려 대상이 아니었습니다.

서버 쪽 API 호출을 병렬화하거나 튜닝하는 방법도 검토는 했지만, 백엔드 API가 여러 팀에 걸쳐 있어서 단기간에 구조를 바꾸기 어려웠고, 설령 병렬화해도 "전부 끝나야 응답한다"는 일괄 응답 구조 자체는 남아 근본 해결이 아니라고 판단했습니다. 그래서 프론트엔드에서 통제 가능한 CSR 전환으로 방향을 잡아, CDN에 스켈레톤 UI만 담긴 가벼운 HTML을 별도로 올려두고 그 파일을 데이터 응답과 상관없이 가장 먼저 받아와 화면 뼈대를 즉시 띄운 다음, 데이터는 개별 API 응답이 오는 대로 비동기로 채우는 구조로 바꿨습니다. CDN에서 내려주는 파일이라 서버 처리 시간과 무관하게 항상 빠르게 도착한다는 점이 이 구조의 핵심입니다.

**꼬리질문 4. 구간별 소요 시간은 구체적으로 어떻게 측정하셨나요?**
안드로이드/iOS 웹뷰라 `chrome://inspect`로 원격 디버깅을 연결해서, 데스크톱 Chrome 개발자도구를 웹뷰에 그대로 붙여서 봤습니다. Network 탭의 워터폴로 요청별 DNS/연결/TTFB(첫 바이트까지 걸리는 시간)/다운로드 구간이 각각 얼마나 걸리는지 나눠서 봤고, Performance 탭 레코딩으로 First Contentful Paint(첫 콘텐츠가 그려지는 시점)와 Largest Contentful Paint(가장 큰 콘텐츠 요소가 자리잡는 시점)를 같이 확인했습니다. 이미지 로드 완료 시점처럼 커스텀 구간은 코드에 `performance.mark()`/`performance.measure()`를 심어서 콘솔로 따로 확인했습니다. 이렇게 모은 수치로 전체 로딩 시간에서 어느 구간이 가장 큰 비중을 차지하는지 순서를 매겨서, 렌더링 방식/이미지 두 가지로 원인을 좁혔습니다.

**꼬리질문 5. "39% 단축"은 FCP 기준인가요, LCP 기준인가요?**
FCP 기준입니다. CDN에서 스켈레톤 셸이 즉시 내려오면서 화면이 더 이상 비어 보이지 않는 시점이 39% 당겨졌는데, 이게 사용자가 "뭔가 반응하고 있다"고 느끼는 체감 속도에 가장 직접적으로 연결되는 지표라고 판단해서 대표 수치로 보고했습니다.

LCP는 따로 32.8% 개선됐습니다. LCP는 스켈레톤만으로는 안 줄고 실제 콘텐츠(가장 큰 이미지 등)가 화면에 자리를 잡아야 완성되는 지표라서, 다른 방식으로 접근했습니다. LCP 요소를 채우는 데 필요한 API 호출의 우선순위를 앞당기고, 분석/로깅처럼 화면에 바로 안 보이는 덜 중요한 작업은 그 뒤로 미뤄서, LCP 요소가 필요한 데이터를 받는 시점 자체를 앞당겼습니다. 정리하면 FCP는 스켈레톤 셸(CDN)로, LCP는 API 호출 우선순위 조정으로 각각 다른 원인을 짚어서 개선했습니다.

### Q5. 웹뷰 말고, 네이티브 화면(Flutter)의 성능은 어떻게 측정하시나요?
웹뷰는 브라우저 지표(FCP/LCP)로 보지만, 네이티브 화면은 "프레임이 제때 그려지는가"를 봅니다. 화면 주사율이 60Hz면 프레임 하나를 16.6ms 안에 그려야 하는데, 이 시간을 넘기면 끊겨 보이는 걸 **잰크(Jank)**라고 부릅니다. Flutter는 이 과정을 **UI 스레드(위젯 빌드/레이아웃/페인트 기록을 담당하는 Dart 쪽)** 와 **Raster 스레드(그 기록을 받아 실제 픽셀을 그리는 GPU 쪽)**로 나눠서 처리하기 때문에, 느려지는 원인이 둘 중 어느 쪽인지부터 구분해야 합니다.

**측정 도구**:
- **Flutter DevTools의 Performance(Timeline) 뷰**: 프레임마다 UI 스레드/Raster 스레드가 각각 얼마나 걸렸는지 막대로 보여줍니다. 특정 프레임을 눌러보면 그 프레임 안에서 어떤 위젯의 build()가 오래 걸렸는지까지 내려가서 볼 수 있습니다.
- **Performance Overlay**(`showPerformanceOverlay: true`): 앱을 실행한 채로 화면 위에 UI 스레드/Raster 스레드 그래프를 바로 띄워서, 특정 화면/특정 동작(리스트 스크롤 등)에서 실시간으로 빨간 막대(느려진 프레임)가 뜨는지 눈으로 바로 확인할 수 있습니다.
- **DevTools CPU Profiler**: 특정 구간에서 어떤 함수가 CPU를 많이 쓰는지 샘플링해서 보여줍니다. 불필요하게 자주 재빌드되는 위젯을 찾을 때는 "Track widget rebuilds" 옵션으로 어떤 위젯이 왜 다시 그려지는지도 확인합니다.
- **DevTools Memory 뷰**: 힙 스냅샷을 비교해서 메모리 누수(예: dispose 안 된 컨트롤러/스트림 구독이 계속 쌓이는 것)를 찾습니다.
- **`Timeline.startSync()`/`finishSync()`(dart:developer)**: 특정 함수 구간에 직접 마킹을 심어서, DevTools 타임라인에서 그 구간만 따로 얼마나 걸렸는지 확인할 수 있습니다. 웹뷰 성능 측정 때 `performance.mark()`로 커스텀 구간을 쟀던 것과 같은 개념입니다.

**측정할 때 주의할 점**: 반드시 `flutter run --profile`(프로파일 모드)로 측정해야 합니다. 디버그 모드는 에셔션 체크 등 개발 편의를 위한 오버헤드가 붙어 있어서 실제 배포 성능보다 훨씬 느리게 나오기 때문에, 여기서 잰 수치는 신뢰할 수 없습니다.

**네이티브 레벨(플랫폼별)까지 더 깊게 봐야 할 때**: Android는 Android Studio Profiler(CPU/메모리/네트워크)나 `adb shell dumpsys gfxinfo <패키지명>`으로 프레임별 렌더링 시간 통계를 볼 수 있고, iOS는 Xcode Instruments의 Time Profiler나 Core Animation 도구로 FPS와 GPU 사용량을 확인할 수 있습니다. Flutter DevTools에서 원인이 명확히 안 잡히면 이쪽까지 내려가서 봅니다.

### Q3. SQL은 어느 정도 다뤄보셨나요?
MySQL과 DynamoDB로 서비스 데이터를 직접 처리했고, 아우토크립트 자산관리 시스템에서 306명, 1,471건 규모의 데이터를 조회/이관하는 쿼리를 직접 작성했습니다.

**꼬리질문 1. 조회 쿼리가 느려지면 어떤 순서로 원인을 찾으시나요?**
먼저 실행 계획(EXPLAIN)을 봐서 풀 스캔이 일어나는지 확인하고, 인덱스가 없거나 조건절이 인덱스를 못 타는 구조인지 봅니다. 그다음 조인이 많다면 꼭 필요한 컬럼만 가져오는지, N+1처럼 반복 쿼리가 발생하는 구조는 아닌지 확인합니다.

## 4. CS 기본기 — Flutter/App/웹 중심 (실제 포지션 기준으로 재구성)

*Flutter 경력자가 APP 운영(1순위)/레거시 웹 운영(2순위)에 합격했으므로, 기술 CS 질문은 백엔드/DB보다 Flutter/앱/웹뷰/브라우저 쪽에서 나올 확률이 훨씬 높음. Flutter 면접 후기, iOS/Android 신입 면접 후기, 프론트엔드 CS 단골질문을 두루 검색해서 실제로 가장 자주 나오는 주제 위주로 정리함.*

### 4-A. Flutter/Dart 기본기

**Q. StatelessWidget과 StatefulWidget의 차이는?**
StatelessWidget은 한 번 만들어지면 내부 상태가 바뀌지 않는 위젯으로, 부모가 새 데이터를 넘겨줄 때만 다시 그려집니다. StatefulWidget은 State 객체를 따로 가지고 있어서 setState()를 호출하면 자체적으로 다시 그려질 수 있습니다. 오초이스에서는 화면 대부분을 StatelessWidget으로 만들고, 실제로 값이 바뀌는 부분(재생 상태, 로딩 여부)만 StatefulWidget이나 Riverpod 상태로 분리했습니다.

**Q. BuildContext가 뭔가요?**
위젯 트리에서 지금 위젯이 어디 위치해 있는지를 나타내는 핸들입니다. `Theme.of(context)`, `Navigator.of(context)`처럼 트리를 거슬러 올라가며 가장 가까운 조상을 찾을 때 씁니다. 위젯이 dispose된 뒤에 context를 쓰면 크래시가 나서, 비동기 작업 뒤에 context를 쓸 때는 `mounted` 체크를 하는 습관이 있습니다.

**Q. Widget 생명주기(라이프사이클)를 설명해주세요.**
StatefulWidget은 `createState()`로 State 객체가 만들어지고, `initState()`가 한 번 호출된 다음 `build()`가 호출돼 화면을 그립니다. 데이터가 바뀌면 `didUpdateWidget()`을 거쳐 다시 `build()`가 호출되고, 화면에서 빠지면 `dispose()`가 호출됩니다. 오초이스에서 WebView 컨트롤러나 애니메이션 컨트롤러처럼 리소스를 쥐고 있는 객체는 `initState()`에서 생성하고 `dispose()`에서 반드시 해제했습니다.

**Q. Flutter에서 "dirty"가 뭔가요? setState()를 호출하면 정확히 무슨 일이 일어나나요?**
Flutter는 내부적으로 세 개의 트리를 가지고 있습니다. **Widget 트리**(그냥 설정값, 매번 새로 만들어지는 불변 객체), **Element 트리**(화면에 실제로 붙어서 상태를 유지하는 실체), **RenderObject 트리**(실제 레이아웃 계산과 그리기를 담당)입니다. setState()를 호출하면 해당 Element에 `markNeedsBuild()`가 호출되면서 그 Element가 **"dirty(더러움/갱신 필요)"** 상태로 표시되고, 프레임워크가 관리하는 "다시 그려야 할 Element 목록"에 등록됩니다.

다음 프레임이 그려질 때 프레임워크는 이 목록에 있는 dirty한 Element들만 골라서 build()를 다시 호출합니다 — **전체 위젯 트리를 다 다시 그리는 게 아니라, dirty로 표시된 부분만** 다시 그립니다. 새로 나온 Widget 설정과 기존 Element를 비교(타입과 key가 같은지)해서, 같으면 Element를 재사용하며 내용만 갱신하고, 다르면 기존 Element를 버리고 새로 만듭니다. 레이아웃/그리기 자체가 바뀌어야 하면 RenderObject 쪽에도 `markNeedsLayout()`/`markNeedsPaint()`로 별도의 dirty 표시가 되어, 실제 픽셀을 다시 그리는 Raster 단계까지 이어집니다.

**꼬리질문. 그럼 불필요한 리빌드(dirty 처리)를 줄이려면 어떻게 하나요?**
세 가지를 봅니다. 첫째, **const 생성자**를 쓸 수 있는 위젯은 const로 선언합니다 — 내용이 절대 안 바뀌는 게 컴파일 타임에 보장되면 Flutter가 그 Element를 아예 dirty 목록에 넣지 않고 건너뜁니다. 둘째, setState()를 호출하는 범위를 최소화합니다 — 화면 전체를 감싸는 최상위 위젯에서 setState()를 부르면 그 아래 전부가 dirty가 되니, 실제로 바뀌는 부분만 별도 위젯으로 쪼개서 그 안에서 상태를 갖게 합니다. 셋째, Riverpod/Provider를 쓸 때도 `Consumer`로 감싸는 범위를 최소 단위로 좁히거나 `select()`로 필요한 필드만 구독해서, 상태 객체 전체가 아니라 실제로 쓰는 값이 바뀔 때만 dirty가 되게 만듭니다. DevTools의 "Track widget rebuilds"를 켜면 어떤 위젯이 얼마나 자주 dirty가 되는지 실시간으로 확인할 수 있습니다.

**Q. key는 왜 쓰나요?**
같은 타입의 위젯이 리스트에서 순서가 바뀌거나 추가/삭제될 때, Flutter가 어떤 위젯이 어떤 위젯인지 구분할 수 있게 해주는 식별자입니다. key가 없으면 Flutter가 위치 기준으로 위젯을 재사용해버려서, 리스트 아이템의 상태(예: 선택 여부)가 엉뚱한 아이템으로 넘어가는 버그가 날 수 있습니다.

**Q. Future와 Stream의 차이는?**
Future는 한 번의 비동기 작업이 끝나면 값을 하나 주고 끝나지만, Stream은 값을 여러 번에 걸쳐 계속 보내줄 수 있습니다. API 응답 하나를 받아올 때는 Future를, 실시간으로 계속 값이 들어오는 경우는 Stream을 씁니다.

**Q. Isolate는 왜 필요한가요?**
Dart는 기본적으로 싱글 스레드(메인 Isolate)에서 동작해서, 무거운 연산을 메인에서 돌리면 화면이 멈춥니다(프레임 드랍). Isolate는 별도 메모리 공간을 가진 독립된 실행 단위라서, 무거운 연산을 다른 Isolate로 보내 메인 스레드를 막지 않게 합니다. Isolate끼리는 메모리를 공유하지 않고 메시지로만 통신합니다.

**Q. 상태관리(Provider/Riverpod)를 쓰는 이유는?**
setState()는 그 위젯과 자식들만 다시 그리지만, 여러 화면에서 공유해야 하는 상태(로그인 여부, 재생 상태)는 위젯 트리를 넘나들며 전달해야 합니다. 오초이스에서는 Riverpod의 StateNotifierProvider로 셋톱박스 페어링 상태를 연결/기기/콘텐츠 단위로 분리 관리해서, 상태가 바뀌면 그 상태를 구독하는 화면만 정확히 다시 그려지게 했습니다.

**먼저 용어 정리** *(아래 표에 나오는 단어들)*
- **보일러플레이트(Boilerplate)**: 매번 거의 똑같이 반복해서 써야 하는 코드. 로직 자체는 별거 없는데 "이렇게 써야 동작한다"는 규칙 때문에 어쩔 수 없이 반복하는 코드 뭉치. 상태 하나 만들 때마다 클래스 선언, 초기화, 리스너 등록을 매번 비슷하게 써야 한다면 그게 보일러플레이트.
- **InheritedWidget**: Flutter가 기본 제공하는, 위젯 트리 위쪽에서 아래쪽 모든 자손에게 데이터를 전달할 수 있게 해주는 특수 위젯. Provider 같은 라이브러리들이 내부적으로 이걸 기반으로 만들어짐.
- **컴파일 타임 vs 런타임**: 컴파일 타임은 코드를 실행하기 전에 빌드(변환)하는 시점, 런타임은 앱이 실제로 실행되고 있는 시점. "컴파일 타임에 오류를 잡는다"는 건 앱을 실행해보지 않고 빌드하는 순간 바로 에러를 알려준다는 뜻 — 실행한 뒤에야 터지는 런타임 오류보다 훨씬 안전함.
- **러닝커브(Learning curve)**: 어떤 기술을 배워서 익숙해지기까지 걸리는 노력/시간. "높다"는 배우기 어렵다, "낮다"는 금방 익힐 수 있다는 뜻.
- **DI(Dependency Injection, 의존성 주입)**: 어떤 객체가 필요로 하는 다른 객체를 스스로 만들지 않고 외부에서 만들어서 건네받는 설계 방식. 화면이 API 서비스 객체가 필요할 때 직접 새로 만들지 않고 밖에서 미리 만들어진 걸 받는 식. 테스트할 때 가짜(mock) 객체로 바꿔 끼우기 쉬워짐.
- **안티패턴(Anti-pattern)**: 겉보기엔 편해 보이지만 실제로는 유지보수/확장성 측면에서 좋지 않다고 알려진 설계 방식. 커뮤니티에서 "이렇게 하지 마세요"로 자주 지적되는 패턴.

**Q. 상태관리 라이브러리들 장단점을 비교해주세요.**

| 방식 | 장점 (쉽게 풀면) | 단점 (쉽게 풀면) |
|---|---|---|
| **setState** | 제일 간단함. 화면 하나 안에서만 값이 바뀌면 되는 경우 쓰기 좋고, 추가로 아무것도 안 깔아도 바로 쓸 수 있음 | 다른 화면까지 그 값을 알려줄 수는 없음. 화면이 많아지면 관리하기 힘들어짐 |
| **Provider** | Flutter를 만든 팀이 공식으로 추천하는 방법이라 배우기 쉽고 예제도 많음. 앱을 무겁게/느리게 만들지 않음 | 상태 하나 만들 때마다 비슷한 코드를 계속 반복해서 써야 함. 서버에서 데이터를 받아오는 것처럼 복잡한 상황엔 손이 많이 감 |
| **Riverpod** | 코드에 실수가 있으면 앱을 실행하기도 전에 미리 알려줌(실행 중 갑자기 앱이 죽는 일이 줄어듦). 화면과 따로 떼어내서 상태만 테스트해볼 수 있음. 여러 데이터를 조합해서 쓰기 편함 | 배워야 할 개념이 많아서 처음 접하면 헷갈림 |
| **Bloc/Cubit** | "이 버튼을 누르면 → 상태가 이렇게 바뀐다"는 흐름이 딱 정해져 있어서, 여러 사람이 같이 만들어도 서로 헷갈리지 않음 | 간단한 화면 하나 만드는 데도 써야 하는 코드가 많아서 번거로움 |
| **GetX** | 상태 관리, 화면 이동, 객체 관리를 한 가지 도구로 다 처리해서 전체 코드 양이 적음 | 안에서 어떻게 동작하는지 잘 안 보여서, 문제가 생기면 원인을 찾기 어려움. 다른 개발자들 사이에서 "권장하지 않는다"는 의견이 많음 |

오초이스에서 Riverpod를 택한 이유는, 셋톱박스 페어링처럼 상태가 연결/기기/콘텐츠 단위로 복잡하게 얽혀 있어서 컴파일 타임 안전성과 상태 조합 기능이 필요했기 때문입니다.

**Q. Hot Reload와 Hot Restart의 차이는?**
Hot Reload는 코드 변경분만 다시 컴파일해서 현재 앱 상태는 유지한 채 화면만 갱신합니다. Hot Restart는 앱을 처음부터 다시 시작해서 상태가 초기화됩니다. main() 함수나 전역 변수, 초기화 로직을 바꿨을 때는 Hot Reload로 반영이 안 될 수 있어서 Hot Restart가 필요합니다.

### 4-B. Android/iOS 플랫폼 기본기 (Flutter가 그 위에서 돌아가는 실제 기반)

*Flutter는 네이티브 위에 얹힌 프레임워크라, 그 아래 Android/iOS가 어떻게 동작하는지 모르면 "왜 이 버그가 iOS에서만 나는지" 같은 질문에 답이 막힘. APP 운영 직무는 스토어 배포/네이티브 이슈 대응도 포함되므로 자주 나오는 주제 위주로 정리.*

**Q. Android 4대 컴포넌트는 무엇인가요?**
Activity(화면 단위 UI), Service(화면 없이 백그라운드에서 도는 작업), BroadcastReceiver(시스템/앱 이벤트 수신), ContentProvider(앱 간 데이터 공유)입니다. Flutter 앱은 실제로는 FlutterActivity라는 Activity 하나 위에서 전체 화면을 그리는 구조라서, 네이티브 플러그인을 직접 다룰 때는 이 4대 컴포넌트와의 연동 방식을 알아야 합니다.

**Q. Activity 생명주기를 설명해주세요.**
onCreate() → onStart() → onResume()으로 화면이 보이고, 다른 화면이 위에 뜨면 onPause(), 완전히 안 보이면 onStop(), 다시 돌아오면 onRestart()→onStart()→onResume(), 종료되면 onDestroy()가 호출됩니다. Flutter는 이 생명주기를 WidgetsBindingObserver로 감싸서 AppLifecycleState(resumed/inactive/paused/detached)로 단순화해서 노출하는데, 오초이스에서 앱이 백그라운드로 갈 때 영상 재생을 일시정지시키는 로직을 이 상태 변화를 감지해서 구현했습니다.

**Q. ANR(Application Not Responding)이 뭔가요?**
메인(UI) 스레드가 일정 시간(보통 5초 안팎) 응답하지 않으면 안드로이드가 강제로 띄우는 경고창입니다. 메인 스레드에서 네트워크 호출이나 무거운 연산을 동기적으로 돌리면 발생합니다. Flutter의 메인 Isolate도 같은 역할이라서, 무거운 연산은 별도 Isolate로 빼서 메인 스레드를 막지 않아야 ANR/프레임 드랍을 피할 수 있습니다.

**Q. iOS 앱 생명주기를 설명해주세요.**
Not Running 상태에서 실행되면 Inactive(전환 중)를 거쳐 Active(포그라운드, 상호작용 가능)가 되고, 홈으로 나가면 Background(제한된 시간 동안만 작업 가능)로, 시간이 지나거나 시스템이 메모리를 회수하면 Suspended(메모리엔 있지만 코드는 실행 안 됨)로 넘어갑니다. Flutter의 AppLifecycleState.paused가 iOS의 Background/Suspended에 대응합니다.

**Q. iOS는 메모리를 어떻게 관리하나요?**
ARC(Automatic Reference Counting)로, 어떤 객체를 참조하는 곳이 하나도 없어지면 자동으로 메모리가 해제됩니다. 다만 A가 B를 강하게 참조하고 B도 A를 강하게 참조하는 순환 참조(retain cycle)가 생기면 둘 다 해제가 안 돼서 메모리 누수로 이어지는데, 그래서 클로저나 델리게이트 참조에는 weak/unowned를 씁니다. Dart는 가비지 컬렉터 방식이라 메커니즘은 다르지만, 웹뷰 컨트롤러나 스트림 구독을 dispose 안 하면 똑같이 메모리 누수가 생겨서 항상 dispose()를 챙기는 습관이 있습니다.

**Q. Android 런타임 권한과 iOS 권한 요청 방식의 차이는?**
Android 6.0(API 23) 이상은 카메라/위치/마이크 같은 위험 권한을 설치 시점이 아니라 실행 중 필요한 순간에 사용자에게 묻는 런타임 권한 모델입니다. iOS도 최초 사용 시점에 시스템 팝업으로 묻지만, 한 번 거부당하면 앱에서 다시 팝업을 못 띄우고 설정 앱으로 유도해야 하는 차이가 있습니다. 오초이스 심사 반려 사유가 "권한 사용 목적 설명 부족"이었는데, iOS는 Info.plist에 권한별 사용 목적 문자열(Usage Description)을 반드시 넣어야 심사를 통과합니다.

**Q. Android 백그라운드 실행 제약은 어떤 게 있나요?**
Doze 모드(기기가 오래 정지 상태면 백그라운드 네트워크/작업 제한), App Standby(안 쓰는 앱의 백그라운드 활동 제한), Android 8.0 이후 백그라운드 서비스 시작 제한 등이 있습니다. 그래서 정확한 시각에 실행돼야 하는 작업은 WorkManager 같은 시스템 API로 예약해야, 시스템이 배터리 최적화와 절충해서 실행해줍니다.

### 4-C. 웹뷰/하이브리드 앱 구조 (프로젝트 1과 직결)

**Q. 웹뷰와 네이티브 화면의 차이, 왜 웹뷰를 쓰나요?**
네이티브 화면은 앱을 다시 빌드/배포해야 바뀌지만, 웹뷰 화면은 서버의 웹 콘텐츠만 바꾸면 스토어 심사 없이 바로 반영됩니다. 오초이스에서는 콘텐츠 탐색 화면처럼 자주 바뀌는 부분을 웹뷰로, 재생 화면처럼 성능이 중요한 부분을 네이티브로 나눴습니다.

**Q. 네이티브와 웹(JS) 사이 브릿지는 어떻게 동작하나요?**
`webview_flutter` 같은 패키지가 JavaScript channel을 제공해서, 웹 쪽에서 정의된 channel 이름으로 메시지를 보내면 네이티브(Dart) 쪽 콜백에서 받습니다. 반대로 네이티브에서 웹으로 값을 보낼 때는 `runJavascript()`로 JS 함수를 직접 실행시킵니다. 오초이스에서는 이 구조로 웹 화면의 액션을 받아 네이티브 화면을 띄우는 식으로 연동했습니다.

**Q. 웹뷰 앱에서 흔히 겪는 문제는 뭐가 있나요?**
초기 로딩이 네이티브보다 느린 것, 웹뷰 인스턴스를 화면마다 새로 만들면 메모리를 계속 잡아먹는 것, iOS/Android 웹뷰 엔진(WKWebView vs Chromium 기반)이 달라서 같은 CSS/JS가 플랫폼별로 다르게 렌더링되는 것이 대표적입니다. 오초이스에서는 웹뷰를 화면 전환마다 새로 만들지 않고 재사용하는 구조로 바꿔서 메모리 문제를 줄였습니다.

### 4-D. 브라우저/프론트엔드 CS (레거시 웹 운영 대비)

**Q. 브라우저가 HTML을 받아서 화면에 그리기까지 과정을 설명해주세요.**
HTML을 파싱해서 DOM 트리를, CSS를 파싱해서 CSSOM 트리를 만들고, 이 둘을 합쳐서 실제로 화면에 그려질 요소만 담은 렌더 트리를 만듭니다. 그다음 각 요소가 차지할 위치/크기를 계산하는 레이아웃 단계, 마지막으로 실제 픽셀을 채우는 페인트 단계를 거칩니다. 오초이스 웹뷰 성능 개선 때 이미지 크기를 미리 지정 안 해두면 레이아웃이 여러 번 다시 계산되는 문제가 있어서, 이미지 크기를 CSS로 미리 고정해뒀습니다.

**Q. 리플로우(Reflow)와 리페인트(Repaint)의 차이는?**
리플로우는 요소의 크기/위치가 바뀌어서 레이아웃을 다시 계산하는 것이고, 리페인트는 레이아웃에 영향을 안 주는 스타일(색상 등)만 바뀌어서 다시 칠하는 것입니다. 리플로우가 훨씬 비용이 커서, 애니메이션은 가능하면 transform/opacity처럼 리플로우를 안 일으키는 속성으로 만드는 게 좋습니다.

**Q. 자바스크립트 이벤트 루프를 설명해주세요.**
자바스크립트는 싱글 스레드라 한 번에 하나의 작업만 실행합니다. 동기 코드는 콜스택에서 순서대로 실행되고, setTimeout이나 fetch 같은 비동기 작업은 백그라운드에서 처리된 뒤 콜백이 태스크 큐에 쌓입니다. 이벤트 루프는 콜스택이 비었을 때 큐에서 콜백을 꺼내 실행하고, Promise 같은 마이크로태스크는 일반 태스크보다 먼저 처리됩니다.

**Q. CORS는 왜 생기고 어떻게 해결하나요?**
브라우저가 보안을 위해 현재 페이지와 다른 출처(도메인/포트/프로토콜)로 가는 요청을 기본적으로 막는 정책입니다. 서버가 응답 헤더에 Access-Control-Allow-Origin을 명시하면 브라우저가 그 응답을 허용합니다. 아우토크립트 자산관리 시스템에서 프론트(React)와 백엔드(Spring Boot) 도메인이 달라 CORS 오류가 났었는데, 서버에 허용 오리진을 등록해서 해결했습니다.

### 4-E. 네트워크 기본기

**Q. HTTP와 HTTPS의 차이는?**
HTTP는 평문 통신이라 중간에서 가로채거나 변조할 수 있지만, HTTPS는 TLS로 암호화해서 내용을 보호합니다. 처음 연결할 때 TLS 핸드셰이크로 서버 인증서를 검증하고 암호화 키를 교환합니다. 홈초이스에서 SSL 인증서를 적용해 전 구간을 HTTPS로 전환한 경험이 있습니다.

**Q. TCP와 UDP의 차이는?**
TCP는 연결을 맺고 순서/도착을 보장하는 대신 느리고, UDP는 그걸 보장 안 하는 대신 빠릅니다. 일반 API 통신은 TCP(HTTP) 위에서 동작하고, 실시간성이 중요한 스트리밍 등은 UDP 계열을 쓰기도 합니다.

**Q. HTTP 상태 코드 몇 가지를 설명해주세요.**
200은 성공, 201은 생성 성공, 400은 클라이언트 요청 자체가 잘못됨, 401은 인증 안 됨, 403은 권한 없음, 404는 리소스 없음, 500은 서버 내부 오류입니다. 상태 코드만 보고도 어느 쪽 문제인지 구분할 수 있게 구분해서 씁니다.

### 4-F. 백엔드/DB (레거시 웹 운영 보조 대비, 기존 정리 유지)

### Q. REST API를 설계할 때 어떤 원칙을 지키시나요?
자원(Resource) 단위로 URI를 설계하고, 행위는 HTTP 메서드(GET/POST/PUT/DELETE)로 표현합니다. 예를 들어 "사용자를 삭제한다"를 `/deleteUser`처럼 URL에 동사를 넣지 않고 `DELETE /users/{id}`로 표현하는 식입니다. 상태 코드도 200/201/400/404/500처럼 의미에 맞게 구분해서 클라이언트가 응답 코드만 보고도 상황을 판단할 수 있게 합니다.

### Q. Spring에서 트랜잭션은 어떻게 관리하시나요?
`@Transactional`로 서비스 계층에서 트랜잭션 경계를 관리합니다. 여러 테이블에 걸친 작업 중간에 하나라도 실패하면 전체가 롤백되도록 해서 데이터 정합성이 깨지지 않게 합니다.

**꼬리질문. 트랜잭션 안에서 외부 API를 호출하면 어떤 문제가 생길 수 있나요?**
외부 API 응답이 느리면 그동안 DB 커넥션을 계속 붙잡고 있어서 커넥션 풀이 고갈될 수 있고, 외부 호출이 실패했을 때 이미 커밋된 것처럼 보이는 정합성 문제도 생길 수 있습니다. 그래서 외부 API 호출은 트랜잭션 밖으로 빼거나, 실패 시 재처리할 수 있는 별도 구조(상태값 + 재처리 API)로 분리하는 게 안전하다고 생각합니다. 실제로 아우토크립트 헬프데스크 자동화에서 Teams Webhook 연동을 만들 때도 전송 성공/실패 상태를 별도로 관리하고, 실패 건만 재처리하는 구조로 분리했습니다.

### Q. 동시에 같은 데이터를 여러 요청이 수정하려고 하면 어떻게 처리하시나요?
낙관적 락(버전 컬럼 비교)과 비관적 락(SELECT FOR UPDATE) 중 상황에 맞게 고릅니다. 충돌이 드물게 일어나는 경우라면 낙관적 락으로 충분하고, 충돌이 자주 예상되는 재고/결제 같은 데이터는 비관적 락으로 확실히 막는 편이 낫다고 생각합니다.

## 4-1. AI 활용 질문 (나올 확률 높음 — 원래 AX 지원자였기 때문)

### Q. AI 도구를 실무에 어떻게 활용하시나요? / AI보다 본인이 더 잘하는 건 뭔가요?
Claude Code나 Codex로 코드/문서 초안을 빠르게 뽑고, **제가 보증할 수 있는 범위와 아닌 범위를 나눠서** 검증합니다. FAQ 챗봇을 AI로 만들 때, 기본적인 질문-답변 매칭 구조는 AI가 잘 만들었지만 "관리자가 퇴사하거나 서버 장애가 나면 이 구조가 어떻게 깨지는가"는 AI가 먼저 짚어주지 않았습니다. 그 부분은 제가 직접 판단해서 이중화 구조로 다시 설계해달라고 요청했습니다.

자산관리 시스템 만들 때도 AI가 뽑은 코드 초안에서 CORS 오류나 데이터 이관 중 항목 누락이 있었는데, 그건 로그를 직접 찍어보며 원인을 좁혀서 제가 고쳤습니다. **AI가 만든 결과물을 그대로 쓰지 않고, 실패하는 조건을 제가 먼저 의심해보고 깨뜨려보는 게 제 역할**이라고 생각합니다.

## 5. 인성/상황 질문 (압박 후속질문 포함)

### Q. 단점은 무엇인가요?
원인을 찾기 시작하면 끝을 봐야 직성이 풀리는 편입니다. 방화벽 장애처럼 큰 문제는 이 성향 덕에 잘 잡는데, 사소한 이슈에도 똑같은 태도로 덤비면 시간이 아깝다는 걸 최근에 알았습니다. **(개선)** 지금은 이슈가 들어오면 먼저 "이게 지금 끝까지 파고들 문제인가"를 판단하고, 아니라면 시간을 정해두고 그 안에서만 봅니다.

### Q. 팀원과 의견이 부딪힌 경험이 있나요?
*(실제 사례로 답변 준비 필요 — 헬로tv/딜라이브 마이그레이션처럼 팀 4인 프로젝트에서 있었던 구체적 상황을 하나 골라, 문제 상황 → 내가 검토한 대안 2가지 이상 → 그중 하나를 선택한 이유 → 결과 순서로 정리해둘 것. 알려주시면 이 문서에 채워넣겠습니다.)*

**예상 꼬리질문 1. 그때 팀원이 끝까지 본인 생각에 반대했다면 어떻게 하셨을 것 같나요?**
**예상 꼬리질문 2. 지금 돌아보면 그 판단이 최선이었다고 생각하시나요, 아쉬운 부분은 없나요?**

### Q. 가장 힘들었던 경험과 극복 방법은?
로드밸런싱 환경에서 방화벽 정책이 바뀔 때마다 통신이 끊기는 장애가 반복됐던 상황입니다. 재연결로 덮으면 당장은 넘어갈 수 있었지만, 며칠 뒤 같은 문제가 또 터질 걸 알면서 방치할 수는 없었습니다. 로그를 구간별로 뜯어보며 프록시 서버 IP 변경 이력을 확인했고, IP를 Elastic IP로 고정하는 구조로 인프라를 재구성해서 재발을 막았습니다.

**꼬리질문. 만약 그 방법으로도 재발했다면 다음 대안은 뭐였을까요?**
Elastic IP 고정이 실패했다면, 방화벽 정책 변경 시점에 자동으로 감지해서 알림을 주는 모니터링을 먼저 붙이고, 근본 원인이 방화벽 쪽 정책 관리 프로세스 자체에 있다고 보고 방화벽을 관리하는 팀과 정책 변경 시 사전 공유하는 프로세스를 만드는 쪽으로 접근했을 것 같습니다.

### Q. 낯선 기술을 빠르게 익혀야 했던 경험은?
오초이스 웹뷰 성능 이슈를 맡았을 때, 그전까지는 서버 사이드 렌더링만 다뤄봤지 클라이언트 사이드 렌더링으로 아키텍처 자체를 바꿔본 적은 없었습니다. 문서로 이론부터 정리하기보다 화면 하나를 먼저 CSR로 바꿔보고 스켈레톤 UI가 실제로 어떻게 동작하는지 눈으로 확인한 다음, 나머지 화면으로 범위를 넓혀갔습니다. 처음 접하는 영역이라도 실제로 동작하는 작은 예시부터 만들어보면서 익히는 방식이 저한테 맞습니다.
